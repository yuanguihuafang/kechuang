# 本地知识数据生命周期统一标准设计

日期：2026-10-20  
状态：实施中；定向测试进行中；全量后端测试和真实服务验证未完成  
范围：仅本地 `D:\Work\kechuang` 代码、测试和文档；不连接、不修改或部署服务器。

## 1. 目标与边界

将管理控制台、用户文档入口、草稿发布、解析图片、Milvus 索引和智能问答纳入同一套可核对、可重试的流程，减少 PostgreSQL、MySQL、MinIO 与 Milvus 之间的状态漂移。

本设计复用现有应用服务、任务记录、幂等键和 Outbox/补偿，不引入新的全局工作流引擎，不重写存储层，不修改线上数据。实现仅针对本地代码和测试。

成功标准：

- 同一业务来源的 PostgreSQL、MySQL、MinIO、Milvus 记录可用稳定 ID 交叉核对；重试不产生重复业务记录或向量。
- 任何部分失败都明确标记失败/待补偿，不显示为完成；重试使用同一来源身份并可安全重放。
- 管理界面、文档读取、图片展示和问答结果遵循相同的发布状态、权限、来源和图片可用性规则。
- 读请求不隐式修改对象存储或业务记录。
- 管理员重新解析后，在新结果重新发布前，前端不再展示该附件的旧解析原文和旧字段提取结果；重新发布成功后整组切换为新结果。
- 封面图和解析原文图片统一使用同一受控 URL 规范，前端不需要区分两套路径。
- 每次发布前执行完整预检；任一权威记录、活动版本、原件/产物/图片、业务记录或目标索引不满足契约时，阻断发布并明确报告原因。

## 2. 数据权威与身份

| 数据 | 权威存储 | 稳定关联键 | 派生/校验规则 |
|---|---|---|---|
| 草稿字段、人工修改、已确认分块 | PostgreSQL | `draft_id`、`source_id` | 重新解析不得重新提取或覆盖人工字段；仅显式编辑可改字段 |
| 文档、版本、发布/回收状态 | PostgreSQL 生命周期目录 | `document_id`、`version_id` | 发布只能引用所属文档的当前有效版本 |
| 业务记录 | MySQL | `(knowledge_type, mysql_id)` | 发布重试更新同一记录；不得因重解析另建重复业务行 |
| 原文件、解析产物、图片对象及清单 | MinIO | 原件按 `storage_key`；图片按 `(document_id, image_id)` | 清单到对象键的映射必须可读取；对象键不暴露为前端 URL |
| 检索向量 | Milvus | `(knowledge_type, mysql_id)` 或附件来源组键 | 仅为派生索引；按明确来源组替换，不作为字段或发布状态的权威来源 |

`source_id` 表示相关草稿/附件组，不替代 `mysql_id`。同一来源组可有多个业务记录或附件；不得把不同 `mysql_id` 合并成一条业务结果。管理员已发布草稿优先保留其 `mysql_id`、`source_id` 和人工确认字段。

## 3. 统一操作协议

涉及跨存储的写操作一律按以下阶段执行：

1. **预检**：验证操作者权限、记录归属、发布状态、活动版本、关联 ID、冲突及对象可读性；生成明确的来源组变更清单。预检不写业务存储。
2. **保护**：对不可逆清理/替换记录本次操作 ID、目标 ID、受影响对象和可恢复快照；普通可重试更新沿用现有任务/Outbox 机制，不复制整库备份。
3. **幂等写入**：按已有应用服务更新权威记录和派生数据；以稳定业务 ID 更新，不按标题猜测或新建重复记录。替换 Milvus 时先校验新请求，再精确删除/替换目标来源组。
4. **逐层校验**：回读 PostgreSQL、MySQL、MinIO、Milvus 的本组结果，核对状态、行/向量数量、ID、图片引用和版本关系。
5. **完成或补偿**：全部必要步骤通过后才标记最终成功；部分失败记录完成步骤、失败阶段和可重试动作。恢复必须重放原操作身份，不能静默切换到另一来源或扩大清理范围。

业务状态更新与外部存储不能组成单一数据库事务。因此实现应依赖现有任务/Outbox 补偿和幂等写，而不是宣称跨库原子性。删除区分下架、回收和彻底清理；彻底清理前必须确认共享草稿、共享附件和同组业务记录的影响。

## 4. 流程要求

### 4.1 管理员与用户文档 CRUD

- 所有入口先验证身份和文档/版本所有权；用户入口不可操作管理员数据，管理员入口遵循显式授权。
- 上传先建立明确的文档/版本关系，再记录原文件键、解析任务及派生产物；重复提交由幂等键归并。
- 文档更新产生新版本或按现有版本契约更新，不覆盖仍被草稿引用的旧版本数据。
- 下架只改变可见/可检索状态；回收保留可恢复数据；彻底清理处理全部关联引用并保留可审计结果。
- 用户逻辑删除草稿后立即从个人中心隐藏；已删除草稿满 30 天后统一由每日北京时间 02:00 的清理任务彻底删除。未发布用户/管理员草稿 30 天未更新后清附件并保留草稿字段；已发布草稿及其关联附件绝不自动清理。清理前检查来源组、附件、业务记录及版本共享引用，存在引用或状态不确定时跳过。审计事件保留 180 天后由同一清理时段清理。
- 管理控制台目录、用户文档列表、MCP 工具和 HTTP API 共用同一权限与发布状态判定，不在前端自行推断权限。

### 4.2 解析、编辑、草稿与发布

- 重新解析生成待发布结果，不调用字段提取，不覆盖现有草稿字段、`mysql_id` 或 `source_id`。管理端在待发布期间隐藏该附件的旧解析原文和旧字段提取结果，避免旧值被误认为新解析结果。
- 重新发布成功时，将新解析原文、分块、图片资产和本次明确确认的字段作为一个逻辑替换整体生效；失败时继续显示明确的待处理/失败状态，不混合展示旧解析与新解析。业务身份按既有稳定 ID 保留，不因重解析重复造 MySQL 记录或 Milvus 业务项。
- 若重解析生成新图片 ID，必须同步更新该文档的解析块、已确认草稿来源块、封面引用和对应索引请求；不可更新某一层后就报告修复完成。
- 字段提取是独立、显式的步骤；失败时保留已保存解析原文和旧草稿，不残留误导性的成功状态。
- 发布验证附件与当前活动版本一致，写入/更新原 MySQL 业务记录，按业务来源组替换 Milvus，再保存最终索引快照和生命周期状态。失败时留下任务及补偿状态，不伪造已发布。
- 每次发布都必须先校验 PostgreSQL 草稿/文档/版本关系、MySQL 目标记录身份、MinIO 原件及本次引用的解析产物和图片对象、Milvus 来源组替换目标与冲突；预检失败不得执行发布写入。必要的写入后回读校验通过后才显示发布成功。
- 草稿更新或重发时，只有请求明确提交空值的字段才清空 MySQL 对应字段。

### 4.3 图片及路径

- 管理的 MinIO 图片唯一对外格式为 `/api/v1/perception/images/{document_id}/{image_id}`；封面图与解析原文图片均使用此格式，只有图片清单能把该 ID 映射到对象键。Aliyun 等外部图片 URL 原样保留。
- 上传、解析、原文编辑、发布、检索和详情展示复用现有规范化函数，不在各调用点自行拼桶名、宿主机路径、旧域名或 `derived/` URL。
- **解析结果 GET 必须纯读取**：不能保存或修补图片清单、解析结果、PostgreSQL 或索引。清单修复只能经显式写接口/任务执行，并记录修改前后差异。
- 显式修复和发布预检验证图片清单引用的 MinIO 对象确实存在；面向用户返回图片时，只呈现已确认可读的映射。校验范围限于本次响应/来源组实际引用的图片，不在每次请求中扫描整桶。
- 删除图片前先检查解析原文、草稿封面/字段、其他版本和索引中的引用；不得因单个编辑视图隐藏图片而清掉仍被引用的对象。

### 4.4 智能问答与检索

- 候选检索、重排、引用展开和联网兜底不得绕过知识库类型、`PUBLISHED` 状态或身份权限过滤。
- 一张业务卡片按 `(knowledge_type, mysql_id)` 识别；同一业务记录的不同 chunk/来源优先合并展示，不得将不同 `mysql_id` 混为一项。
- 引用文档、版本和图片必须能回溯到同一有效来源；图片使用受控地址且可读取。详情可展示完整内容，摘要/卡片按现有限制展示。
- 联网搜索只在检索候选为空且符合现有联网策略时触发；相关性判断失败时遵循现有 fail-closed 规则，不伪装成知识库命中。

## 5. 失败、并发和安全

- 并发更新按 PostgreSQL 版本号/预期版本做乐观冲突检测；过期版本或跨文档附件必须拒绝，不自动套用到最新版本。
- 外部 MinIO/Milvus 失败必须保留清晰失败阶段和安全重试信息；不吞异常、不静默切换桶/Collection/来源。
- 修复操作默认 dry-run，apply 需有精确目标和显式确认；禁止仅按文件名、标题或相似内容自动归并。
- 日志与报告记录任务 ID、文档/版本/草稿/MySQL/source ID、动作、数量和结果；不得记录密码、Token 或文件正文。
- 任何服务端数据修复、服务器登录、部署、Collection 切换和批量清理均不属于本地实现授权。

## 6. 实施分段与验收

实施拆为三个顺序阶段，每阶段先补失败用例再修实现：

1. **读写边界和图片**：GET 无 MinIO 写入；对象缺失/映射歧义不返回伪有效图片；封面与原文图片共用受控 URL，外部 URL 规则保持；显式修复才改变清单。
2. **文档/草稿生命周期和管理 CRUD**：测试 owner/version/status 校验、重解析后的旧原文/字段隐藏与重新发布整体切换、重复发布复用 ID、附件共享、发布全量预检、下架/回收/清理边界、跨库部分失败及补偿重试。
3. **问答检索与统一流程文档**：测试发布与权限过滤、来源分组、图片证据、联网兜底和流式终态；更新项目文档索引，给出本地标准操作/验收清单。

每阶段运行对应 Pytest；后端阶段完成后运行后端完整测试，前端触及展示契约时运行对应前端测试。可运行本地依赖集成测试时验证本地 PostgreSQL、MySQL、MinIO、Milvus；不启动或连接服务器。每个标准流程验收需同时检查：

- PostgreSQL 状态/版本和关联 ID；
- MySQL 目标业务行唯一且值正确；
- MinIO 原件/解析产物/图片清单及实际对象存在性；
- Milvus 仅有预期来源组记录，无旧角色或重复业务 ID；
- 管理目录与问答只返回应发布、应授权的内容；
- 失败注入后可见、可重试，且重试不重复造数。

## 7. 不在范围内

- SSH、服务器文件、服务器数据库/对象存储、线上部署或服务重启。
- 真实线上数据修复、Collection 重建/切换和批量删除。
- 新增全局工作流引擎、全库迁移、无关 UI 改版或依赖升级。
- 对所有历史状态作“永不出错”的保证；目标是检测、阻止静默不一致并安全恢复。
