# 管理端跨存储清理与恢复设计

## 目标与边界

统一文档删除、版本 purge、草稿发布/删除的跨存储操作，避免 PostgreSQL、MySQL、Milvus、MinIO 只完成一部分却被标记为成功。复用现有 PostgreSQL Task/Outbox，不增加数据库或依赖；跨库不承诺 ACID 回滚，失败后按已完成步骤幂等前向重试。

本次不处理定时清理策略，不修改 OPIEos。管理界面只做重建确认提示，不扩展其他前端功能。

## 1. 文档 ID 删除与版本 purge

- 管理端按文档 ID 删除和生命周期版本 purge 共用同一清理编排，覆盖该文档及其关联草稿、未被其他活动草稿共用的 MySQL 业务记录/向量、关联 MinIO 对象、Milvus 文档/草稿向量和 PostgreSQL 生命周期状态。
- 共享业务记录不能因删除一个文档/草稿而误删；保留现有引用检查边界，只清理确认不再被其他活动记录引用的数据。
- 在执行外部副作用前，先持久化 Task/Outbox 操作意图；记录每个清理步骤，重复执行安全，失败或进程中断后由现有处理器继续前向重试。外部清理全部成功后，才将生命周期记录置为最终 `PURGED`/删除状态。失败时保留可恢复任务，不提前标记清理完成。
- 两个入口维持各自现有权限与请求契约，只复用后端清理逻辑。

## 2. 按知识类型重建 Collection

2026-10-05 用户变更：本节以[Milvus 加载修复与仅索引重建](../../方案/Milvus加载修复与仅索引重建.md)为准。只重建指定 Collection，保留 PostgreSQL/MySQL 业务记录、文档版本与 MinIO 文件；仅重置所选知识类型的同步控制断点。删除前核验持久化来源并保存恢复意图，完整回灌必须显式调用恢复接口。本次不改测试前端，不再实施重建后的业务清理。

## 3. 草稿发布与删除的前向恢复

- 在共享草稿发布应用服务和草稿删除应用服务中复用 Task/Outbox，覆盖 REST、管理台及 MCP 等现有调用入口。
- 执行外部副作用前持久化操作意图，再执行 MySQL、Milvus、MinIO、PostgreSQL 各步骤；记录每步进度，所有步骤采用现有幂等键/逻辑保证重复执行安全。失败或进程中断时由 Outbox 重试未完成步骤，不做跨库回滚。
- 只有 MySQL/Milvus/MinIO 清理或写入及 PostgreSQL 最终更新都成功后，才写最终发布/删除状态。失败状态保留在可重试任务中，不伪装为成功。
- 不新增表；步骤进度复用现有 Task 记录，重试复用 Outbox 处理器，不引入第二套任务机制。

## 验收

1. 文档 ID 删除与版本 purge 均清理关联对象；共享业务记录被其他活动草稿引用时保留；任一步失败可重试，成功后 PostgreSQL 生命周期状态与对象存储/向量状态一致。
2. 重建一种知识类型仅清空该 Collection，保留业务记录和文件，重置该类型的同步控制断点；显式恢复有效公开索引，其他 Collection 不变。
3. 重建和恢复均需 `confirm=true`；本轮测试前端不作改动，使用维护 API 验证。
4. 草稿发布/删除在各外部步骤失败和重试时不重复产生业务记录、不丢失可恢复进度，最终状态只在所有步骤成功后写入。
5. 运行相关后端定向测试；不连接或修改线上服务与数据，不执行定时清理。
