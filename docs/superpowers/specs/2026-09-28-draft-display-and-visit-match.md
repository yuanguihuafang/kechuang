# 草稿字段展示与拜访记录匹配确认

## 规则

- 智能问答编辑器只展示 `draft_contracts.py` 当前草稿类型合同中的字段，不追加模型/MCP 返回的额外字段；必填状态与草稿合同一致。方案草稿只显示一个 `pub_dept`，界面标签为“发布企业名称”；`company` 的既有值合并到 `pub_dept` 后不再作为独立字段。成果的 `company` 按合同语义显示为“发布单位”。
- 客户拜访记录仍是内部记录，不作为公开知识库草稿发布。用户点击拜访记录的发布/确认保存后，保存成功再询问是否按记录中的潜在需求做供需匹配；匹配必须由用户主动点击，不自动执行。
- 首页三条示例均明确请求供需匹配，点击时固定传 `supply_demand_match`，不让模型再决定是否创建草稿。
- 不调整需求、成果草稿字段，不改变管理台 `full` 提取或公开 API；成果草稿的 `category` 显示为“成果类型”，`analyse_contect` 显示为“成果分析”。

## 验收

- 各类编辑器均不展示合同外字段；方案草稿只显示“发布企业名称”，成果草稿的 `company` 显示为“发布单位”、`category` 显示为“成果类型”、`analyse_contect` 显示为“成果分析”。
- 拜访记录确认保存成功后出现中文匹配确认及“匹配相关供应商”操作；拒绝/忽略时不触发检索。
- 首页三条示例点击均携带 `intent_hint: supply_demand_match`。

## 实施与验证

- 前端表单字段和必填状态收敛到草稿合同；方案 `company` 值合并到 `pub_dept` 后不再作为表单/提交字段。拜访记录成功保存后追加一次用户确认式匹配提示，只有点击按钮才调用匹配流程。
- 首页示例文案改为明确的供需匹配场景，点击固定传 `supply_demand_match`。成果 `company` 展示名为“发布单位”。
- 验证：前端 Node 回归 9 项通过，Vite 构建通过；Backend 字段提取/合同回归 20 项通过，定向 Ruff 通过。未启动或重启服务。
