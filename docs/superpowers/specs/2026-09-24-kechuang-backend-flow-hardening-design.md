# 科创 DeerFlow 迁移链路与后端基础能力收口设计

> 2026-09-28：本文为历史设计。共享 `kc-*` 已迁至原生 public 目录，解决个人 Custom 技能导致不加载的目录问题；旧问答执行图已退役。当前状态以[完整重构验收](2026-09-28-kechuang-final-refactor.md)和[迁移方案](../../方案/DeerFlow迁移与Skill接入方案.md)为准。

> **状态（2026-09-24）：** 后端链路修复仍有效；本机 Agent 使用标准文件式存储，MCP 工具仍为 Gateway 全局共享。OPIEos 标准 Skill 存储在用户拥有个人 Custom Skill 时可能不加载仓库共享 `kc-*` Skill，且 `/skills/custom` 不展示共享 `LEGACY` Skill；这项限制当前未解决。服务器 Agent 与认证部署方式需由 OPIEos 维护方确认。当前状态见 `docs/DeerFlow迁移与Skill接入方案.md`。

## 目标

修复科创问答迁移到 DeerFlow 后已发现的链路断点，并审查当前聊天、文件解析、匹配、草稿及 Skill 运行路径所依赖的后端基础能力；前端 API、请求参数和用户既有流程保持不变。

## 用户要求与约束

- 科创项目通过 OPIEos 标准 Agent 存储加载 `kechuang`；业务能力通过 `kc-*` Skills 和 Gateway 共享的 MCP 工具提供，业务 Backend 仍负责身份与数据权限校验。
- DeerFlow 已启用时，聊天和上传解析后的编排走同一 Agent/runtime；DeerFlow 关闭或未配置时，保留旧 Supervisor 路径。DeerFlow 已启用但运行失败时必须明确失败，不能悄悄改走旧链路。
- 保留快速入口及其既有业务流程；DeerFlow 每轮负责意图识别和流程判断，不替换前端交互流程。
- 保持现有 `/api/v1/*` 路由、请求参数及已有响应字段兼容；不触碰 `D:\Work\kc-rag-agent`，不提交代码。
- 以本地测试为主，不启动或重启用户服务，不修改用户本地 `.env`。

## 设计

### 1. 匹配方向与草稿动作

只从明确的 `draft_type`、`knowledge_type`、匹配方向、当前会话/草稿上下文推导草稿类型。不能把缺失类型默认为“需求”。供给找需求和需求找供给的匹配结果必须保留各自方向；方向或草稿类型不足以安全生成“立即补充”动作时，不生成指向错误草稿的动作。会话中已发布草稿的普通后续消息应能恢复匹配上下文，不要求前端每轮重复发送整份草稿。

### 2. 上传解析与聊天编排

文件解析器及其输出格式保持现状。DeerFlow 可用时，将解析摘要/结构化字段作为明确标记的资料上下文传入 `kechuang` Agent，按非可信材料处理，不把材料内的文字当作系统或用户指令；同一 `thread_id` 下继续保存用户消息、解析结果、Agent 结果及必要状态。流式与非流式解析使用同一编排选择规则。DeerFlow 关闭或未配置时继续调用旧 Supervisor。

### 3. 流式结果、匹配卡片与持久化

适配器必须把上游 SSE 的 `error` 事件传为业务错误；若流意外结束且没有明确终止事件，不能合成成功。匹配工具结果统一规范化为现有前端匹配卡片消费的结构。DeerFlow 与旧 Supervisor 完成结果后使用现有持久化能力记录会话、匹配结果和审计摘要，避免同一请求重复写入；历史/审计存储异常不应吞掉已经生成的答案，但需要有带 `trace_id` 的可检索日志。

### 4. Skill 运行时与管理列表

仓库 `skills/custom` 中的科创全局 Skill 与用户自己的 Custom Skill 必须同时可发现、可启用，并能被 `kechuang` Agent 的 Skill manifest 使用。全局仓库 Skill 仍为只读；`/skills/custom` 页面应能展示这些共享 Skill，同时区分其只读属性，用户个人 Skill 的编辑/删除权限不变。同步当前 Skill 数量及清单测试，移除已删除 Skill 的陈旧断言。

当前 OPIEos 基线并不满足本节的“共存”和管理列表显示要求：用户级目录存在个人 Custom Skill 时，存储实现不会再扫描全局 `skills/custom`；`/skills/custom` 接口只筛选 `CUSTOM` 类别。由于当前约束是不改 OPIEos 核心，此要求暂列为维护方待处理项，不得以历史计划中的测试记录声称已完成。

### 5. 后端基础能力审查

审查当前科创迁移链路及其直接依赖中的：

- trace/request/thread/user 标识从 API、DeerFlow run、MCP 工具到业务持久化的传递和隔离；
- 总处理耗时、检索耗时、首 token 耗时的测量起点、终点及当前响应字段语义；
- 并发请求和同会话请求的共享状态、竞态及用户/会话隔离；
- 审计和匹配记录是否在两种编排路径一致、是否重复或静默丢失；
- 关闭/未配置回退与运行中故障之间的边界；
- DeerFlow client、MCP、Supervisor 和业务服务之间是否通过现有适配/契约隔离；
- 已有幂等键在会产生副作用的 MCP/草稿/客户拜访流程中的覆盖与重复请求行为。

只修改有测试或代码证据支持、且属于上述链路的缺陷。复用已有契约、锁、指标和存储，不新建通用编排框架；不新增公共接口或要求前端发送新参数。与当前链路无关、需要数据迁移/部署改造的发现另行列出。

## 验收标准

1. `supply_to_demand` 不会因缺少请求类型而被改成需求草稿；方向明确时“立即补充”使用正确草稿类型。
2. 上传解析后继续对话能沿用同一 DeerFlow 会话和解析上下文；关闭/未配置 DeerFlow 时旧路径仍可用。
3. 上游 SSE 错误明确返回失败，缺少终止事件不会被报告为成功；运行耗时不会回到 `0 ms` 或把首 token 时间误作总耗时。
4. DeerFlow 和旧 Supervisor 的会话、匹配记录、审计摘要行为一致且不会因正常重试而重复记录；持久化失败有可定位日志。
5. **当前未满足（待 OPIEos 维护方处理）：** 仓库 `kc-*` Skills 在用户已有个人 Skill 时仍可加载；共享 Skill 在“自定义 Skill”列表可见且只读。
6. 匹配输出继续驱动现有匹配卡片；保留快速入口流程和前端既有请求/响应契约。
7. 相关并发/隔离/幂等测试通过；不调用真实外部模型，不要求启动服务作为单元测试前置条件。

## 实施边界

- 当前实施不修改 OPIEos DeerFlow 核心 Skill runtime/API；仅维护合法内部认证 Header、Agent/Skill/MCP 配置与业务资产。若要满足本设计中未关闭的 Skill 存储/列表要求，需 OPIEos 维护方另行批准并实现；只有确认卡片契约必须调整时才改测试前端。
- 不删除旧 Supervisor、不改 OPIEos 其他项目的 Agent 行为、不改数据库结构、不升级依赖、不做全仓无关重构。
- 并行工作只分配给互不重叠的文件范围；上传链路与最终结果持久化由一个协调者整合并做端到端验证。
