# Backend 上传链路修复与冗余审查计划

## 目标

先完成已确认的上传解析、草稿字段和用户可见错误修复，再对 `backend` 做一次基于调用关系的冗余审查。只删除或合并能证明无调用或语义完全重复的实现；不把“文件较长”当作冗余依据。

## 顺序与验收

1. **上传与草稿回归**：新增失败测试覆盖 `draft_only` 新字段进入卡片字段、SSE 区分解析失败与解析后失败；补充 Agent 默认简体中文规则；验证 PPTX/图片当前源码的 PaddleOCR 路由并重启本机 Backend。真实 OCR 外部调用需用新的测试资料单独验证，不自动重放用户文件。
2. **Backend 全面审查**：读取 Backend 文档与模块边界；使用静态调用图及仓库搜索检查重复转换/校验逻辑、无调用私有符号、失效分支和无效包装层；删除前核对全部调用方与现有测试。不得触碰 `.env.local`、OPIEos/DeerFlow 核心、稳定 API/数据契约、权限/审计/错误处理或仍在用的入口。
3. **逐项验证**：每个行为修复和每项确定的冗余清理均运行对应测试；最后运行 Backend 全量 pytest、Ruff，并同步 `docs/Agent.md` 的结果和未覆盖项。

## 风险边界

- 当前工作区有大量未提交修改，全部视为用户改动；不得用重置、批量格式化或整目录删除来“清理”。
- 静态无引用不等于无运行时入口；路由注册、插件/Agent 动态发现、反射调用和外部导入均须先排除。
- 不新增兼容/兜底行为；清理遇到不确定的兼容入口或业务语义时保留并记录，不擅自删改。
- 用户日志在知识检索完成处结束，不能据此断言后续失败原因。
