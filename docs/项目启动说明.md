# Windows 本机开发启动说明

- DeerFlow Gateway、Next.js 前端、Nginx：在 Windows 本机通过 `make dev` 启动；Gateway 监听 `8001`。
- PostgreSQL、Milvus、MinIO、etcd、Attu：通过科创项目自己的 `backend/docker-compose.local.yml` 启动。
- Redis 属于 OPIEos/DeerFlow Docker 本地运行配置；原生 `make dev` 不会自动启动它，只有确实需要时才单独启动 Redis 服务。
- 科创业务 Backend 在单独的 Conda `py311` 环境以前台方式运行，监听 `8793`；`D:\Work\kechuang\frontend` 是可选测试界面。

聊天传输说明：科创前端只连接 `POST /api/v1/chat/stream` 的 SSE；Backend 再以 HTTP 请求 OPIEos 的 `POST /api/threads` 和 `POST /api/threads/{thread_id}/runs/stream`。这是 Gateway 的 run-stream API，不是 MCP Streamable HTTP。`/mcp/` 是 Agent 调用科创工具的独立 MCP 通道。每轮一个 HTTP 客户端，轮内复用连接池；不是每个 token 建立 TCP 连接。当前 run 超时默认 300 秒。

Milvus 生命周期：每个 Backend worker 首次访问时懒建立一条连接，问答检索和管理控制台的 Collection 操作复用该连接；Collection 句柄仍各自管理，连接失效后按代次重取。Backend 正常关闭时统一断开；多 worker 部署时每个 worker 各自建立一条连接。管理和问答仍走各自服务及权限检查。

边界说明：科创数据依赖只由 `backend/docker-compose.local.yml` 管理；
OPIEos Compose 仅配置 DeerFlow 本地 Docker 运行方式，不包含科创数据依赖或业务 Backend。
服务器上已有 DeerFlow 时，部署科创 Backend 并配置连接现有 Gateway，不需要再部署一套 DeerFlow。

当前 Gateway、前端和 Nginx 使用宿主机 `make dev`。不要在此模式下不指定服务直接启动整个 OPIEos Compose，否则会额外启动容器版 Gateway、前端和 Nginx。

## 一、启动 Docker 数据服务

```powershell
Set-Location 'D:\Work\kechuang\backend'
docker compose -f docker-compose.local.yml up -d postgres minio etcd standalone attu
```

PostgreSQL 默认数据库名为 `kechuang`，Backend 的 `backend/.env.local` 中 `DATABASE_URL` 也应指向该库。首次初始化或数据库迁移更新后，在启动 Backend 前执行：

```powershell
conda activate py311
Set-Location 'D:\Work\kechuang\backend'
alembic upgrade head
```

PostgreSQL 池按每个 Backend worker、每个 DSN 限额，默认总上限约 18 条（psycopg 8 + SQLAlchemy 4+2 + Checkpointer 4）。部署增加 worker 时按 worker 数乘以每 DSN 上限估算 PostgreSQL `max_connections`；可通过 `POSTGRES_POOL_MAX_SIZE`、`POSTGRES_SQLALCHEMY_POOL_SIZE`、`POSTGRES_SQLALCHEMY_MAX_OVERFLOW` 和 `LANGGRAPH_CHECKPOINT_POOL_MAX_SIZE` 调整，非法配置会在建池时直接报错。详见[连接池预算与生命周期](superpowers/specs/2026-09-27-postgres-pool-lifecycle.md)。

启动 OPIEos Compose 中的 Redis：

```powershell
Set-Location 'D:\Work\kechuang\OPIEos'
docker compose --env-file .env -f docker/docker-compose-dev.yaml -p kechuang up -d redis
```
OPIEos 内部持久化使用 config.yaml 中的默认 SQLite；OPIEos 本地 .env 不设置 DATABASE_URL。科创业务 Backend 的 PostgreSQL 配置独立管理。

## 二、启动 DeerFlow/OPIEos 本机服务

激活 Conda 环境 `deerflow`（Python 3.12）以提供当前 shell 工具环境。注意：`make dev` 实际通过项目的 `uv` 环境 `OPIEos\backend\.venv` 运行 Gateway，不是直接用 Conda Python；不需要把 DeerFlow 依赖另装到 Conda 环境。每个新开的 PowerShell 窗口都要设置以下环境，再运行项目命令：

```powershell
conda activate deerflow

$uvRoot = 'D:\uv-data'
$env:UV_NO_CONFIG = '1'
$env:UV_PYTHON_INSTALL_DIR = "$uvRoot\python"
$env:UV_TOOL_DIR = "$uvRoot\tools"
$env:UV_TOOL_BIN_DIR = "$uvRoot\bin"
$env:Path = "D:\Work-use\nginx-1.30.5;$uvRoot\bin;$env:Path"

Set-Location 'D:\Work\kechuang\OPIEos'
make check
make dev
```

`make check` 用于检查 Node.js、pnpm、uv、Nginx 等本机依赖；环境没有变化时不必每次运行。首次安装依赖或依赖发生变化时运行 `make install`。`make dev` 会同步项目依赖，并在前台启动：

- Gateway：`localhost:8001`
- DeerFlow 前端：`localhost:3000`
- 本机 Nginx 反向代理：`localhost:2026`

保持终端运行；按 `Ctrl+C` 停止。必要时在项目目录运行 `make stop` 清理本机服务。

本机 `kechuang` Agent 由 `DEERFLOW_AGENT_OWNER_USER_ID=62ddcc4d-f2b5-4152-be26-78a1a7554a86` 解析，运行目录为 `OPIEos\backend\.deer-flow\users\62ddcc4d-f2b5-4152-be26-78a1a7554a86\agents\kechuang`；源码资产在 `OPIEos\agents\kechuang`。每次更新 Agent 后都要在启动前同步 `config.yaml` 和 `SOUL.md`，不能只在目录缺失时复制，否则会一直运行旧 SOUL。

```powershell
$sourceAgentDir = 'D:\Work\kechuang\OPIEos\agents\kechuang'
$runtimeAgentDir = 'D:\Work\kechuang\OPIEos\backend\.deer-flow\users\62ddcc4d-f2b5-4152-be26-78a1a7554a86\agents\kechuang'
New-Item -ItemType Directory -Path $runtimeAgentDir -Force | Out-Null
foreach ($agentFile in 'config.yaml', 'SOUL.md') {
    Copy-Item -LiteralPath (Join-Path $sourceAgentDir $agentFile) -Destination (Join-Path $runtimeAgentDir $agentFile) -Force
    if ([IO.File]::ReadAllText((Join-Path $sourceAgentDir $agentFile)) -cne [IO.File]::ReadAllText((Join-Path $runtimeAgentDir $agentFile))) {
        throw "Agent 同步校验失败：$agentFile"
    }
}
```

若设置了自定义 `DEER_FLOW_HOME`，运行目录应为 `<DEER_FLOW_HOME>\users\<DEERFLOW_AGENT_OWNER_USER_ID>\agents\kechuang`。只同步以上两个业务资产，不复制或清理用户会话、数据库、记忆。必须使用与 Backend 配置相同的 owner UUID 检查目标目录；不得改成科创业务用户 ID，也不依赖共享目录回退。Agent 配置中的 `skills` 限制可发现的 `kc-*` Skill。修改 Gateway 认证、Agent 或 Skill 后，由运行者重启 Gateway。

离线加载验证必须沿用启动脚本的两个路径变量：`DEER_FLOW_PROJECT_ROOT` 指向 `OPIEos`，`DEER_FLOW_HOME` 指向实际运行目录。只设置前者会改变默认数据根，漏设前者则可能从 `backend/skills` 查找而误报技能缺失。使用 `backend/.venv` Python 调用 `load_agent_soul(..., user_id=实际用户)` 与 `get_or_new_user_skill_storage(...).load_skills(enabled_only=True)`，确认 SOUL 与源码一致且配置的 13 个 Skill 全部存在。

科创 13 个共享 Skill 部署在 `OPIEos/skills/public/kc-*/SKILL.md`，随源码目录加载，不复制到个人 Custom 目录。个人同名 Skill 会覆盖共享版本；不要批量删除个人技能。离线回归：在 `OPIEos/backend` 用 `.venv/Scripts/python.exe -m pytest tests/test_kechuang_skill_manifest.py tests/test_run_timing.py -q` 验证公共加载及计时回调。

## 三、启动科创业务 Backend（需要时）

另开 PowerShell：

```powershell
conda activate py311
Set-Location 'D:\Work\kechuang\backend'
python main.py
```

Backend 默认监听 `8793`。聊天只走 DeerFlow，未启用或未配置返回 503；管理台解析等独立接口不因此回退到旧 Agent。健康检查：

```powershell
Invoke-WebRequest http://127.0.0.1:8793/api/v1/health
```

科创 Backend 通过 `DEERFLOW_BASE_URL=http://127.0.0.1:8001` 直连本机 Gateway，内部 HTTP 请求不继承系统代理。验证 Gateway 本身可用：

```powershell
Invoke-WebRequest http://127.0.0.1:8001/health
```

如果聊天日志显示 `POST /api/threads` 的 `ReadTimeout`，先绕过代理检查 Gateway 是否真正响应：

```powershell
curl.exe --noproxy "*" --max-time 5 http://127.0.0.1:8001/health
Invoke-WebRequest http://127.0.0.1:8793/api/v1/health
```

Gateway `/health` 应快速返回 `{"status":"healthy",...}`。如果端口有监听但 `/health` 超时，说明进程存在不等于 Gateway 正常处理请求；先看 `make dev` 的 OPIEos 终端日志，由你决定是否在该终端手动重启 Gateway。Backend `/api/v1/health` 正常不能证明 8001 正常。当前 timeout 默认 300 秒，Gateway 建 thread 卡住时界面可能长时间显示“处理中”；超时配置见 `DEERFLOW_TIMEOUT_SECONDS`。如果目标是服务器 Gateway，维护方需确认支持合法连字符形式的内部认证 Header；CSRF 由科创 Backend 适配现有双提交机制，不要求修改 OPIEos 中间件（见 [OPIEos 修改记录](方案/OPIEos-main修改记录.md)）。

## 六、日志与常见问题

本机 DeerFlow 日志在项目 `logs` 目录：`gateway.log`、`frontend.log`、`nginx.log`。实时跟随：

```powershell
Get-Content 'D:\Work\kechuang\OPIEos\logs\gateway.log' -Tail 100 -Wait
```

OPIE 模型/工具阶段输出 `event=opie_stage_timing`，带 `run_id`、`stage=model|tool`、`name`、`duration_ms`、`outcome`，不记录提示词或工具正文。一个 run 可有多个阶段；工具内部检索耗时是其子阶段，不应重复相加。业务后端普通 INFO 使用终端默认色，关键阶段绿色，ERROR 红色；非 TTY、`NO_COLOR` 和 JSON 日志无 ANSI。Docker 服务可用 `docker logs --tail 100 <容器名>` 查看。

- Docker 报错路径为 `C:\Users???\.docker\config.json`：在当前 PowerShell 设置 `$env:DOCKER_CONFIG = 'D:\docker-config'` 后再执行 Docker 命令。
- uv 读取中文用户目录下配置失败：保持 `UV_NO_CONFIG=1`，并按上文设置 uv 的本地目录。
- Gateway 报数据库 SSL 参数错误：先确认 PostgreSQL 容器健康、`DATABASE_URL` 使用宿主机地址。本地模式通过 `.env` 的 `PGSSLMODE=disable` 同时配置 asyncpg 与 psycopg；远程数据库需要 TLS 时移除本地禁用项，并按服务端要求配置证书。
- 本机 Nginx 无法启动：确认 `D:\Work-use\nginx-1.30.5` 在当前终端的 `PATH` 中。`make check` 通过只说明 Windows 侧能找到 Nginx；`make dev` 会通过 Git Bash 启动它，还需确认 Git Bash 也能解析该命令。

在项目目录用 Git Bash 包装脚本单独验证：

```powershell
.\scripts\run-with-git-bash.cmd -c "command -v nginx && nginx -v"
```

若提示 `nginx: command not found`，在同一个 PowerShell 窗口重新把 Nginx 目录加到 `PATH` 前面，再启动：

```powershell
$env:Path = "D:\Work-use\nginx-1.30.5;$env:Path"
.\scripts\run-with-git-bash.cmd -c "command -v nginx && nginx -v"
make dev
```

## 七、停止服务

在运行 `make dev` 的终端按 `Ctrl+C`，或在项目目录执行 `make stop`。停止 Docker 数据服务时使用 `stop`，不要使用带 `-v` 的删除命令：

```powershell
Set-Location 'D:\Work\kechuang\OPIEos'
docker compose -p kechuang --env-file .env -f docker/docker-compose-dev.yaml stop redis
Set-Location 'D:\Work\kechuang\backend'
docker compose -f docker-compose.local.yml stop
```
