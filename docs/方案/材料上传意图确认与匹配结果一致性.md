# 材料上传意图确认与匹配结果一致性

## 2026-10-09 设计与实现范围

- 普通对话仍由 Agent/LLM 逐轮识别意图；前端不增加字段，继续使用已有 `thread_id`、`message`、`intent_hint`、`intent_confirmation` 和 `draft_context` 合同。
- 用户明确要求检索或匹配时，按该请求直接执行。只有上传材料、没有明确检索意图时，Agent 根据材料识别可能的业务意图并先询问确认；确认前后端工具边界禁止执行知识检索，避免模型在追问前已产生检索卡片。
- 将待确认的意图、匹配方向、查询文本和附件/草稿上下文保存在原会话。仅同一会话中的明确肯定答复可确认并继续；明确拒绝取消。用户改问其他问题时不得把旧确认误用到新请求。
- 确认追问先复述已识别的处理方向，再询问是否开始；供需匹配须明确说出匹配方向。识别不确定或缺少匹配方向时，说明不确定点并给出“检索匹配、整理草稿、仅总结”等可选处理方式，不把未识别内容说成已判断。
- 确认后检索结果卡片是候选事实的唯一来源。助手匹配结果说明只可概括实际返回的卡片，不可自行补称未返回的方案、成果、专家或企业；材料摘要与匹配结果说明分开。
- 候选卡片顺序沿用检索/重排结果，不按类别配额重排，也不强行平衡类别。
- 会话批次状态从实际返回并展示的卡片保存查询、方向、业务意图与稳定结果 ID；无有效历史批次时，换批返回明确的可恢复提示，不抛出未处理异常。
- 不改前端接口、不改服务器、不变更重排排序规则。本地后端实现并验证后，服务器迁移另行进行。

## 实现与验证

- 材料解析后，Agent/LLM 返回的结构化意图用于建立同会话待确认状态；识别失败时不展示模型附带的候选卡片，改为请用户说明希望如何处理资料。
- 已识别意图的追问复述意图/匹配方向，并提示可改为另一匹配方向、整理草稿或仅总结；意图不明确时说明需要用户选择的方向。
- `kc_match`、`kc_retrieval` 和 `kc_profile` 在服务端读取会话闸门，确认前直接拒绝执行。明确确认时复用保存的查询、方向和原附件上下文；上游失败则恢复待确认状态，允许用户重试。
- 检索完成后，匹配类工具的最终说明由实际返回的候选卡片约束；换批状态可从显示卡片动作中恢复检索意图。缺少有效历史批次时返回明确提示。
- 未改前端参数或服务器文件；无提交、无部署。
- 验证：相关 6 个测试文件共 142 passed、1 skipped；Ruff 检查通过；`git diff --check` 通过。测试输出含已有依赖弃用/版本警告。
