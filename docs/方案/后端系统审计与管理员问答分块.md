# 科创后端系统审计与管理员/智能问答分块

方案日期：2026-10-06；最终验证：2026-10-07。状态：两份计划的本地实现已完成；隔离回归及主协调者自审通过。独立审查工具未能加载工作区，真实依赖联调、服务器回填与部署均未执行。下方旧路径/行号是修改前审计证据，当前模块位置见文末。

实施计划分为[清理与恢复数据安全](../superpowers/plans/2026-10-06-backend-data-safety.md)和[管理员/智能问答模块](../superpowers/plans/2026-10-06-backend-module-boundaries.md)，先数据安全再模块迁移。用户已明确鉴权“保留当前”：第 3、4、9 项鉴权风险本轮不改，不宣称安全门禁已完成；第 10 项仅修原有卡片/详情范围的嵌套脱敏，不扩展模型答案。

## 目标与范围

用户要求系统检查科创后端，并将管理员功能与智能问答功能分块。将“只能问答”理解为“智能问答”。范围仅 `backend`；保留未提交改动，不修改 OPIEos、测试前端、运行配置或真实存储数据，不提交代码。

本轮先检查当前源码与相关隔离测试，输出问题证据和分块方案。没有通过真实依赖联调，不能据此保证线上完整可用。此前 Milvus 修复的 151 项回归只覆盖相关范围，不等于全后端验收。

## 检查范围

- 应用装配与路由：`main.py`、`runtime`、`api/v1`、`admin`。
- 管理员：文档目录、草稿管理、治理与审计、MySQL 同步、Collection 维护。
- 智能问答：身份与会话、流式执行、材料解析、草稿卡片、匹配检索、MCP 上下文。
- 共享能力：Perception/Retrieval、发布与访问规则、PostgreSQL/MySQL/MinIO、任务与 Outbox、LLM/解析器生命周期。
- 横向边界：授权、用户隔离、外部需求脱敏、失败一致性、单向依赖、测试隔离。

## 分块约束

- 优先同一后端进程内按业务模块分块，不默认拆微服务或新增端口。
- 管理员与问答各自拥有路由和业务编排，共用底层能力，不彼此导入 HTTP 路由。
- `main.py` 仅承担统一装配；共享服务不得反向依赖 `admin` 或 `api`。
- 数据契约和 API 路径保持不变；结构拆分与业务修复分步进行，不加兼容分支或自动兜底。
- 审计结论和推荐方案由当前源码证据补充；未核验项明确标注，不以目录存在代替功能验收。

### 优先处理的确定问题

1. **P1：清理引用被截断，可能误删有效 MinIO 文件。** `runtime/bootstrap.py:123` 分别只取最多 10000 条文档、草稿、任务；`services/storage/minio/minio_storage.py:458` 却扫描全桶 `uploads/` 和 `derived/` 并删除未引用对象。10001 条有效来源、最后一条未被其他引用覆盖且超过宽限期时，内存复现会删除原文件和确认正文。应完整分页收集引用，收集不完整或核验失败就中止删除，删除前重查对象归属。不用调大固定 limit 冒充完整性保证。
2. **P1：任务日志保留期与长期恢复来源冲突。** `runtime/workflows/file_workflow.py:451` 将确认正文保存到 MinIO，仅在成功任务保存引用；`services/persistence/retention.py:74` 默认删除 30 天前的成功任务；`admin/index_recovery.py:106` 恢复又必须找到这些任务。没有已发布草稿覆盖的旧公开文档，31 天后可能有正文却无法准备恢复。应将确认引用、确认时的有效身份及版本归属保存到已有版本 `artifact_refs`，一次性核验/回填旧版本后切换为唯一版本来源，再允许任务日志按保留期清理。缺失来源直接报错，不猜路径、不重新解析代替人工确认。
3. **P1：后端管理员路由没有统一授权门禁。** `admin/api/v1/admin.py:34` 路由未配置管理员鉴权依赖；`main.py:88` 仅在请求已经携带 Bearer 时校验，不强制所有管理请求登录。目录隔离不是权限隔离；如果宿主或反代未另行限制，读写、删除和重建接口缺少后端自己的管理员校验。管理员身份必须来自可信认证结果，不从 `user_role`、`operator_id` 或内部人员标记推断。
4. **P1：按 user_id 换发令牌的测试登录边界未收紧。** `api/v1/identity/routes.py:23` 接收 user_id 后，只确认用户存在就签发智能体令牌；没有在该入口校验宿主登录证明。生产接入应验证宿主登录凭证/受信服务调用后再签发，测试用户枚举与测试身份入口不应未经限制开放。当前宿主反代是否限制未现场核验。
5. **P2：单对象生命周期操作通过前 200 条列表查找。** `api/v1/documents/lifecycle.py:45`、`:87` 用 `list_documents(user_id, limit=200)` 找目标；有效文档超过窗口时可返回错误 404。应复用仓储已有 `get_document(document_id, user_id=...)`，保留所有权校验，不靠全表分页查单对象。
6. **P1：删除草稿/文档的共享引用保护不完整。** `admin/service.py:460` 删除单个草稿的 MySQL 行及向量前，没有检查同类型其他活动草稿是否仍引用相同业务 ID。`admin/documents.py:85` 虽保护共用业务行，却仍删除同 ID 向量。应对业务行、向量、附件统一使用按业务类型/记录 ID/私有归属的仓储引用查询，不靠全库有限列表判断；共享来源保留，只删除目标草稿自己可删除的记录。
7. **P1：purge 的首次执行与补偿不一致，可能留下已发布的失效草稿。** `admin/documents.py:548` 先删除向量和文件，再调用草稿逻辑删除；仓储 `workflow_repository.py:311` 会拒绝删除仍为 `PUBLISHED` 的草稿。版本回收没有同时下架草稿时，可在外部数据已删后报错；`runtime/bootstrap.py:166` 补偿又未复用关联草稿清理。应先核验所有关联状态，破坏性操作前拒绝不合法请求；首次执行与补偿调用同一清理业务流程，不能另写简化清理路径。
8. **P1：会话/文档删除同样把最新 10000 条草稿当完整集合。** `admin/service.py:285`、`:407`、`admin/documents.py:38` 按有限列表查目标和共享引用，但 `runtime_repository.py:798` 删除会话时会删除该会话全部 PostgreSQL 草稿。遗漏的旧草稿可能没有清理外部数据就失去引用，或漏掉共享引用造成误删。目标按 ID/会话查询，关联引用按业务键查询；这与第 1 项同属引用完整性问题，需要一起修，而不是只修定时扫描。
9. **P1：MCP 只用线程头解析会话所有者，未校验调用者归属。** `runtime/mcp_server.py:51` 通过线程找会话用户，没有比较已验证的 `request.state.user_id`；匿名或用户 A 提供用户 B 的有效 thread ID，内存复现获得 B 的工具身份。应先校验当前链路已有的用户 Bearer，再校验其会话归属；`X-KC-Thread-ID` 只是定位信息，不是登录凭证。修在科创后端，不默认新增签名方案、固定用户令牌或 OPIE 源码变更。
10. **P1 风险：需求侧嵌套脱敏及模型证据边界仍有遗漏。** `core/governance/redaction.py:154` 递归不继承父级需求类型，`knowledge_type=demand` 下嵌套 `fields.link_tel` 可绕过隐藏。`api/v1/chat/public_result.py:94` 主要处理卡片；原始 MCP 证据、模型答案和 debug 不在同一脱敏边界。前一轮用户只要求卡片/详情隐藏，并接受提示词约束；因此修复嵌套卡片属于现有范围，扩展到模型证据及答案应单独确认。建议复用规则，只处理外部用户看到的他人需求联系人/联系方式，不影响供给侧及用户自己的编辑草稿，不加 LLM 调用。
11. **P2：未发布草稿的最新编辑不保证进入下一轮模型输入。** `services/application/draft_session.py:34` 保存 `active_draft`，但 `execution/supervisor.py:139` 自动恢复主要针对已发布草稿；`deerflow_adapter.py:167` 又只注入 `text/summary`，仅有结构化字段时不会形成消息正文。模型主动调工具可能读回，但不应依赖它猜测。执行前按当前用户/会话草稿 ID 读取最新权威版本，按字段合同构造上下文，不能依赖客户端回传旧草稿。
12. **P2：流式错误没有保存本轮会话失败终态。** `execution/supervisor.py:282` 主要在 done 时持久化，`:391` 超时分支只发 SSE error；上游 error 也会提前结束。在内存复现中，失败轮次仅留下用户消息，可能仍显示旧成功状态。成功、错误、异常共用终态保存，记录本轮 request/trace/run 标识与失败阶段；失败不能冒充成功，部分文本明确标记失败，不自动重试或切换模型。

第 1、2、9—12 项已由独立审查用纯内存替身复现；其他项由当前入口及调用源码核实，第 6—8 项经另一名独立审查交叉核验。未宣称生产接口已遭利用，也未核实服务器文档数量是否已超过阈值。

### 目前的结构问题

- 管理员路由已有 `admin/api/v1/admin.py`；并非所有功能仍挤在一个路由。`main.py` 已分别挂载公共业务路由与管理员路由，应保留这个方向。
- `admin/documents.py:12`、`admin/governance.py:14` 等仍从 `api.v1.schemas` 引用请求模型；问答路由工厂 `api/v1/router.py:54` 又能装配管理员路由。两条入口之间仍有导入边界交叉。
- `GatewayRuntime` 同时承载管理员、问答、文件工作流、任务、存储，且 `require_admin()` 会临时创建业务服务；业务模块拿到完整容器容易访问无关能力。
- 管理服务经 `conversation_service.session_store` 取会话仓储，并直接读问答指标；`admin/documents.py:21` 还从 Perception 路由导入图片补全函数。应显式注入共用会话仓储/指标，把图片补全放在已有共用解析/存储服务，不让管理编排依赖另一个入口的实现。
- 当前 `admin/service.py` 1233 行、`api/v1/chat/routes.py` 1372 行、`api/v1/execution/deerflow_adapter.py` 1033 行。文件大本身不是 bug，但这里确实混合 HTTP、长业务流程、协议转换和任务管理，优先按职责拆，而非按行数拆。
- `runtime/bootstrap.py` 不只有装配，还直接承载附件清理、生命周期补偿和定时业务操作；应让组合根注册已有服务，而不是保存业务实现。
- `api/v1/drafts/routes.py:433` 的用户草稿 router 仍注册管理员下架接口；`runtime/mcp_tools/draft.py:223` 为调用业务函数而构建 HTTP router、按 endpoint 名称查找并构造伪请求。两种入口应直接共用草稿应用服务，管理员路径真正归管理模块。

## 推荐方案：模块化单体

继续一个后端、一个端口、一个 ASGI 应用。分成两个业务模块，复用现有基础设施，不拆数据库、不复制 Agent、不新增服务端口。

```text
backend/
├─ main.py                   # HTTP 应用、基础中间件与模块挂载
├─ admin/                    # 管理员业务模块，保留现有根目录
│  ├─ api/v1/                # 仅管理 HTTP 入参、权限与响应
│  ├─ documents.py           # 管理文档流程
│  ├─ governance.py          # 治理、审核、审计
│  ├─ mysql_sync.py          # 同步任务、断点、进度和停止
│  ├─ index_recovery.py      # Collection 维护与恢复
│  └─ service.py             # 小型管理门面，不继续堆长流程
├─ assistant/                # 智能问答业务模块，逐步迁移现有代码
│  ├─ api/v1/                # 会话、材料、草稿、匹配等用户入口
│  ├─ application/           # 问答流、材料流程、业务结果组装
│  └─ integrations/          # DeerFlow HTTP/SSE 与 KC MCP 适配
├─ agents/                   # 共用 Perception/Retrieval 能力
├─ services/                 # 共用发布、访问规则、存储、模型与解析器
├─ core/                     # 共用契约、业务规则和权限策略
└─ runtime/                  # 组合根、依赖装配、资源生命周期
```

这是职责目标，不要求每个目录立即生成新文件。仅搬迁已有调用链；保留共用发布/索引/访问服务，避免管理和问答各复制一套。管理员会话管理只通过共用仓储/查询服务读数据，不调用问答 HTTP 路由。

### 单向依赖

`main/runtime 装配 → admin 或 assistant → 共用应用服务/Agent → 仓储和外部适配器`。

- `admin` 与 `assistant` 不互相导入路由或应用编排。
- 管理员/问答各自 HTTP DTO 留在各自模块；真正共用的发布、文档、任务数据契约进入已有 `core/contracts`。不建立新的万能 `shared` 目录。
- 共用服务不引用业务路由。业务服务通过现有窄契约/显式参数拿所需依赖，不新增整套容器框架或接口层。
- 配置保留单一来源；不要机械地把所有 `runtime.config` 引用当作循环依赖，也不要一次性大搬配置。
- 统一装配 AdminService，不在容器或路由中临时创建。装配缺失明确报不可用，不自动兜底。
- HTTP 路径、SSE 事件名称、草稿/推荐卡片字段保持不变；内部 Python 导入一次性更新，不保留旧路径转发别名。

### 与双服务拆分的取舍

两个进程能进一步隔离同步和问答的资源，但会引入部署、队列、跨进程锁和资源关闭的问题。目前不为目录分块增加这些复杂度。单进程分块不保证 CPU/GPU 或线程资源互不争用；若后续观测证明长管理任务显著阻塞问答，再设计独立 worker，不能现在声称已实现运行隔离。

## 实施顺序（具体步骤以实施计划为准）

1. **先保护数据。** 统一定时清理、草稿删除、会话删除、文档 purge 的完整引用判断；修复共享业务行/向量保护、发布状态前检及补偿流程，补确认来源保留。增加 10001 条引用、共享业务 ID、发布草稿关联 purge、任务过期后恢复、来源缺失拒绝删除的隔离测试。旧版本引用回填是独立数据操作，实施前另行核对和授权，不自动执行服务器回填。
2. **保留认证边界，记录残留风险。** 用户本轮选择保留当前鉴权，不实现正式登录证明、管理员门禁或 MCP 认证改造。将这些作为独立后续安全任务，不通过目录分块宣称获得权限隔离；需求脱敏仍限卡片/详情。
3. **先解开入口和契约。** 主入口分别挂载两模块；管理员不再依赖用户 HTTP 模型，用户路由不再可选挂管理员。保证 OpenAPI 路径与事件契约不变。
4. **再拆长业务流程。** 从管理服务抽同步/维护职责；从材料路由抽材料应用服务；从问答路由抽流式编排与事件适配，并修复权威草稿上下文恢复和失败终态保存。MCP 与 HTTP 共用应用服务，不互调路由。每次只迁移一条完整链路，结构迁移与行为修复分别测试。
5. **收缩运行时。** 把定时清理/补偿业务移回共用服务，组合根只装配并注册；梳理启动失败、正常关闭和后台任务终止，不先新增多进程。
6. **最后验收与文档。** 更新 `docs/Agent.md`、API 文档和模块边界说明；代码结构变更与功能修复分别验证，不提交或部署未经要求的改动。

## 验收条件

其中匿名管理拒绝、正式管理员授权和 MCP 调用者/thread 身份核验属于后续鉴权验收，不是本轮实现项。以下保留完整目标，当前执行范围以两份实施计划和用户“保留当前”选择为准。

- 匿名管理请求拒绝；普通用户不能操作管理接口；已认证管理员能够执行被授权操作。
- 多用户会话、草稿、原文访问互相隔离；每轮 MCP 仍从当前用户令牌及 thread ID 生成上下文。
- MCP 缺凭据及用户/thread 不匹配均拒绝；草稿保存后下一轮用最新字段；done/error/超时/断流均留下本轮唯一终态，不保留旧成功冒充本轮结果。
- 外部用户需求侧初步卡片和详情隐藏联系人/联系方式，供给侧展示不被误改；不新增 LLM 调用做基础权限校验。
- 问答材料解析、草稿创建/编辑/发布、知识检索、供需匹配、换批、流式结束/失败能返回并持久化正确结果。
- 管理员目录、上传、确认、治理、同步、停止和仅 Milvus 恢复保持有效；数据库业务记录与 MinIO 文件不得因模块拆分被重建或清空。
- 新增静态依赖检查，禁止管理与问答互导、共用服务导入路由；结构迁移不能只靠现有 7 项架构测试证明。

### 功能与数据安全

- 下一轮从当前用户的活动草稿 ID 读取持久化最新字段，客户端旧字段不覆盖权威数据；读取失败不当作“没有草稿”。需求卡片继承父级类型脱敏，明确供给子项保持原样，不增加 LLM 调用。
- done、上游 error、超时、无终态断流、取消都记录本轮唯一终态及 request/trace；失败覆盖旧成功状态，取消继续抛出，不切换模型或自动重试。
- 完整收集文档、历史版本、草稿和任务引用；候选对象删除前重查，读取失败停止。文档目录分页显式使用 `documents`，草稿/任务分页使用 `items`，不用默认值掩盖契约错误。
- 新上传在现有 `version_history` 保存旧版本及确认来源，不在新版本完成前抹掉已确认内容。成功确认正文落入版本 `artifact_refs.confirmed_index_request`，先保存来源再清理旧版本；未迁移的成功任务来源受保留期保护。
- 草稿/会话清理按完整、带类型与私有归属的关联查询预检；共享 MySQL、向量和文件保留，仍发布的关联草稿在破坏性操作前拒绝 purge。
- 清理单版本时若同文档还有有效版本，只处理该版本独占原文件，不删除整份派生产物或关联草稿；首次 purge 和补偿共用流程。版本已提交但任务完成失败时，重放只补原任务终态，不重复外部删除或新增补偿任务。
- 过期草稿读取/保存返回原有 410 提示，不直接删除附件；统一定时清理保护较新的共享草稿和当前/历史有效发布版本。
- ASGI 同一事件循环内，草稿写入/发布、确认节点、生命周期与定时清理共享可重入维护锁；锁不保护其他进程、外部数据库写入或自行创建的另一事件循环，不能当成跨存储事务。正常恢复仍要求维护窗口暂停相关业务写入。
- 启动失败、正常退出和后台任务停止通过 `AsyncExitStack` 关闭已创建资源；schema 检查失败也关闭数据库池，Runner 停止失败仍等待后台任务并清空装配状态。`require_admin()` 缺失时明确 503，不临时创建管理员服务。
- Collection 维护仍只影响选定 Milvus 集合，保留 PostgreSQL/MySQL 和 MinIO。旧确认来源仅通过显式核验/回填工具迁移；缺来源拒绝重建，不猜路径、不重解析、不自动 release/load。

### 实施裁决与代价

1. 使用当前脏工作区，不创建 worktree、不提交或重置；保留原有改动，代价是撤回需按文件核对 diff，不能靠单个提交回滚。
2. 查询/来源任务按非重叠文件并行，耦合编排由主协调者合并；后续子 agent 工作区加载失败后改为本地执行，不反复派发。最终自审弱于独立审查，需部署前另行补足。
3. 共享删除放在 `services/application/draft_cleanup.py`，下架放在 `DraftApplicationService`；图片补全放独立 `document_images.py` 而非挤入生命周期文件。代价是内部调用者一次性更新，没有旧导入兼容层。
4. 同实例引用互斥使用原生 asyncio 锁，不复用仅管理 MySQL 同步的线程锁；代价是同循环维护期间相关写入等待，多进程仍需维护窗口。
5. 回放重新预检并执行可重复步骤，而不盲信历史 completed_steps 跳过；共享引用已变化时要以当前真实来源为准，代价是已完成的幂等向量/文件步骤可能再次调用。
6. 读取过期草稿只提示，不立即物理清理；统一清理保护其他引用。代价是到定时任务执行前仍占用存储。
7. 保留版本历史及完整回填候选快照，不引入新表、备份服务或消息框架；代价是历史查询/维护快照有内存和扫描成本，大库需以后用稳定游标/JSONB 索引优化。
8. 修正旧测试的模块路径、会话仓储/定向查询替身，并隔离审计和材料事实提取；成功材料夹具延长到原有 50 字门槛。代价是测试仍不能替代外部服务验收，没有为过测试增加产品兜底。
9. 原有未触及的审计/展示补全 best-effort 行为不作为本次可靠性改造扩大处理；未引入新的业务算法兜底。现有鉴权风险按用户要求保留，不宣称目录分块就是权限隔离。
