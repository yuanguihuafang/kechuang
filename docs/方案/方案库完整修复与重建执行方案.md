# 方案库完整修复与重建执行方案

日期：2026-10-16  
适用范围：仅 `solution` 方案库。  
目标：在不改动 PostgreSQL 草稿/文档、MySQL 业务表和 MinIO 原文件的前提下，核对并重建方案库向量；能恢复的已发布内容尽量恢复，不能恢复的逐项列明，未经管理员接受不得切换活动库。

## 一、恢复原则

1. **PostgreSQL 是已发布管理员草稿及其人工修改内容的权威来源。**优先保留已发布草稿中的字段和 `source_blocks`，不重新调用 LLM 做字段提取，不用旧 Milvus 内容反向覆盖草稿。
2. **MySQL 是业务记录来源。**一条业务记录若已有可恢复的 PUBLISHED 管理员草稿，向量中以 `admin_draft` 保存一次，沿用原 `mysql_id`、`source_id`，不得再为同一业务记录生成一份 `mysql`。没有可用已发布管理员草稿、但 MySQL 记录本身有效的，才以 `mysql` 写入一次。
3. **附件与业务字段分开判断。**附件原文件缺失不等于草稿字段或 `source_blocks` 缺失；有已确认分块即可按原方案库分块规则恢复检索内容。原 PDF 不存在时，不能声称可下载原件；只需针对缺失文件补传，不要求全库重传。图片引用也必须独立核验对象是否存在。
4. **按既有方案库规则重建。**复用当前方案库索引构建、字段映射、embedding 和分块策略，不引入一套新切块方式。优先使用管理员确认后的草稿/分块；仅在没有这份内容时，使用持久化的解析原文或已确认索引请求。不能据此恢复的来源列为缺失，不臆造内容。
5. **先预检、后恢复、再单独切换。**活动 Alias/旧 Collection 在新影子库完成验证和管理员确认前保持不变。任一未接受缺失、新增错误或来源变化都必须阻止切换。
6. **所有检查按当前数据重做。**此前导出的本地审计包和历史计数只作线索，不代表当前 PostgreSQL、MySQL、MinIO 或线上 Milvus 状态。

## 二、逻辑记录与向量写入规则

`source_id` 是一组业务草稿与解析附件原文的关联键，不是业务记录主键；同一 `source_id` 可以关联多个不同的 `mysql_id` 草稿及多个附件。业务记录以 `(knowledge_type, mysql_id)` 去重，同一个 `mysql_id` 只能有一份业务主记录：存在有效 PUBLISHED 管理员草稿时写 `admin_draft`，否则才写 `mysql`。检索卡片按业务记录键分组，不能把同组不同 `mysql_id` 合成一张卡片。保留原 `source_id`，不加 `batch:` 等恢复标记。

每份附件必须独立保存并校验 `document_id`、`version_id`、原文件 `storage_key` 和自己的解析块；`source_id` 只负责把附件与草稿归组，不可用第一份附件代替整组附件，也不可把同组不同业务草稿合并。索引原文按 `(source_id, document_id, version_id)` 去重，同一附件在一组多个草稿中只写一次。

新文档版本替换当前有效版本的解析块/索引内容，不把旧版本 `source_blocks` 追加到新版本。PostgreSQL 中历史版本可留作审计；恢复只选择与当前有效版本一致的块。若旧记录混存多版本且无法可靠归属，预检列为冲突，不猜测、不覆盖。

重建优先复用 PostgreSQL/MinIO 中完整、已确认的最终索引 chunks（保留原顺序、文本、来源定位和角色）；只有最终 chunks 缺失或校验不完整时才从对应附件解析块重建，并调用该知识类型既有的 chunker 与参数。预检和恢复必须记录采用路径及 chunker/参数；不能以“当前通用默认值”替代既有文档类型策略。

图片统一按两类输出：Aliyun 绝对 URL 原样保留；MinIO 图片以 `(document_id, image_id)` 为稳定身份，PG、MinIO 图片清单、Milvus 检索块及 API 响应统一使用受控地址 `/api/v1/perception/images/{document_id}/{image_id}`。MinIO object key 是内部存储定位，不等同于对外 URL；只由图片清单映射，不让前端拼接桶路径。封面图也必须走同一 URL 归一化入口。MinIO 清理只允许在完整引用盘点、dry-run 列表和保留期确认后进行。

PostgreSQL 是草稿/文档/版本关系的权威存储，MySQL 保留业务行及其业务主键/`source_id`，MinIO 保存原附件和派生图片；Milvus 只保存可重建索引。etcd 是 Milvus 内部元数据，不承载这些业务关联，不直接编辑/清理 etcd；collection/alias 只经 Milvus API 管理。历史数据对齐先输出 dry-run 变更清单，未经单独确认不改写 PG/MySQL/MinIO，也不删除对象或历史版本。

恢复按附件的当前 `document_id + version_id` 判断覆盖范围。草稿关联旧版本时，该旧附件块不进入新库；若文档目录仍有新的有效 PUBLISHED 版本，则单独恢复新版本，预检标明草稿与当前附件版本不一致。附件无法验证时只跳过该附件，不丢弃可恢复的业务草稿或同组其他附件。图片清单引用或 MinIO 图片对象缺失时，预检列出文档、图片 ID/对象键，恢复请求移除失效图片引用，保留剩余文本与有效图片。重发布时，只有编辑请求明确提交为空的字段才同步清空对应 MySQL 列。

| 来源状态 | 向量写入 | 附件/原文处理 |
| --- | --- | --- |
| 有效 PUBLISHED 管理员草稿，字段和分块可恢复 | 草稿业务内容写为 `admin_draft`；关联附件按原索引请求和既有角色写入。该 `mysql_id` 不再写 `mysql` | 原件/图片对象存在则沿用原引用；对象缺失则列出具体对象，不影响可独立恢复的草稿内容 |
| 没有有效 PUBLISHED 管理员草稿，但 MySQL 记录有效 | 写为 `mysql` 一次 | 不伪造管理员草稿或附件关联 |
| 管理员草稿可恢复，但附件原文件缺失且没有持久化分块 | 保留可恢复草稿字段；不可生成的附件内容列为缺失，不凭空补块 | 需要原件下载时仅补传该文件；重新解析/分块需沿用原策略并重新预检 |
| 来源记录冲突、版本不一致、业务记录无效或必要内容不可恢复 | 不把不确定内容写入影子库；逐项列出来源 ID、原因和影响 | 只有经管理员接受的预检缺失项才允许在恢复时跳过 |

注意：`admin_draft` 与附件自身的 `admin_doc`/`agent_doc` 等索引块不是重复写入；需要消除的是同一个业务 `mysql_id` 同时出现 `admin_draft` 和 `mysql` 两份业务记录。恢复报告必须分别列示业务主记录数、附件/原文块数和实际向量行数，不能拿 chunk 数直接当业务记录数。

## 三、当前审计线索（必须在操作前刷新）

截至 2026-10-16 的一次历史盘点记录：曾发现 22 份方案相关来源在 PostgreSQL 草稿中还有 `source_blocks`，可用于恢复向量正文，但原始附件对象可能缺失；另有若干草稿分块为空、发布状态/文档版本不一致或来源关联缺失的记录。历史数字和分类可能重叠，也可能已因后续操作变化，**不能直接据此接受缺失或启动恢复**。

每次正式操作须从新的预检报告重新得到：

- 全部 PUBLISHED 方案草稿及其 `draft_id`、`mysql_id`、`source_id`、版本和块数；
- PUBLISHED 文档/附件及当前有效版本，原文件、解析产物、确认索引请求和图片对象的存在性；
- MySQL 有效记录数，以及被管理员草稿覆盖、需单独写入 `mysql`、关联冲突或无效的数据清单；
- 可恢复数、跳过数及每项跳过原因；活动 Alias/旧 generation、预期影子库行数和资源容量。

检查时不能只看文档目录、MinIO 文件名或 Milvus 总行数；要以 PG 草稿/文档关联、确认索引请求和对象实际可读取结果交叉验证。

## 四、执行步骤

### 修复路径选择

三种处理方式按问题逐条选择，可以组合使用；不能把“重新发布”或“删除重传”当成全库重建的替代品。

| 路径 | 适用条件 | 操作边界 |
| --- | --- | --- |
| 管理控制台更新文档并重新发布 | 原文件/附件可用，且确需修正文档版本、补齐附件引用或重新生成该文档索引 | 单份处理；先保留并核对管理员已确认草稿。重新解析可能覆盖人工修改或改变分块，必须复核字段、分块策略和发布版本，再纳入新的预检 |
| 重建 `solution` Collection 并恢复索引 | 需要统一修复向量、去重或恢复草稿/MySQL 关联 | 作为本次全库规范化的主路径；以 PostgreSQL 草稿、已确认分块、MinIO 及 MySQL 为来源，写入影子库并由管理员单独确认切换 |
| 删除问题记录后重新上传 | 原记录确实错误/不可恢复，且已确认原文件和正确关联信息仍可用 | 最后手段；先明确删除的影响范围。优先更新原 document/version 并保留业务关联，避免删除有效 PUBLISHED 草稿、MySQL 记录或附件后造成新 ID、重复记录或关联断裂 |

决策顺序：先做只读预检；有可恢复的管理员草稿/`source_blocks` 就通过影子库恢复；仅原件缺失且需要下载时，针对该文件补传并保留原文档关联；原文可用但版本/索引确需修正时，在管理控制台单份更新、复核并重新预检；只有源记录本身错误或无法恢复、且管理员确认影响后，才删除并重新上传。修补了来源后必须重新预检，旧预检指纹不能复用。

### 执行前确认门

在完整方案确定前只做只读检查，不更新/重新发布文档、不删除记录、不补传文件、不启动影子恢复。预检结束后先形成一份逐条处置表，至少包含：

- `draft_id`、`document_id`、版本、`mysql_id`、原 `source_id`；
- 管理员草稿字段、`source_blocks`、确认索引请求、原文件和图片对象分别是否存在；
- 每条记录选择的路径（控制台更新发布、影子库直接恢复、针对性补传、删除后重传或跳过）；
- 预计保留/重建/跳过的业务数据和向量块，以及下载、检索、图片展示的影响；
- 需管理员接受的精确缺失清单、操作顺序、验证方法和失败时保持旧 Alias 的方案。

先据此确认完整修复方案和缺失影响，再按批次执行。每批完成并核对后再进入下一批；任何未列明的数据变化都暂停并重新预检。Collection 切换仍须在影子库验证完成后由管理员单独确认，不能把“同意执行修复方案”视为预先授权切换。

### 0. 操作前保护

- 确认所有 Backend 实例运行同一版支持稳定 Alias、影子恢复和管理员确认切换的代码；旧版进程仍以物理 Collection 读写时不得继续。
- 确认 PostgreSQL、MySQL、MinIO、Milvus 可用；核对活动 `solution` Alias 当前目标、磁盘空间、加载内存和影子库额外容量。
- 保留旧物理 Collection；不要手工 drop、清空活动库、改 PG 草稿状态、重置 MySQL 业务数据或删除 MinIO 对象。
- 记录本次维护人、时间、预检 ID 和当前 Alias 目标。不要把密码或 Token 写入本文件或操作日志。

### 1. 只读预检

在管理控制台对 `solution` 发起 Collection 重建预检。预检只读取来源并生成快照/缺失指纹；不得创建、清空或写入 Collection，也不得修改业务 PostgreSQL、MySQL、MinIO 数据。

逐项检查：

1. PUBLISHED 管理员草稿能否从 PostgreSQL 生成完整索引请求；草稿内容是否含管理员确认后的字段和 `source_blocks`。
2. 草稿关联的文档、版本、`mysql_id` 和原 `source_id` 是否相互一致；文档必须是当前有效的 PUBLISHED 版本。
3. 没有管理员草稿覆盖的 MySQL 记录是否有效，且每个 `mysql_id` 只会写一次。
4. 原文件、附件、确认索引请求和图片对象是否存在、可读；区分“向量正文可恢复”与“原文件可下载”。
5. 分块策略是否来自当前方案库既有索引路径；预检不得用新规则重切后直接写线上。

预检输出需要能按具体 ID 下载/查看缺失清单，而不只是返回“有若干失败”。若来源互相冲突或确认请求版本不匹配，必须列为不可恢复/待人工处理，不自动选择一个版本。

### 2. 处理缺失项并复核

- `source_blocks` 已保存、原 PDF 缺失：可按已保存块恢复检索向量；若还要求原件可下载，仅补传该 PDF，并关联到原 document/version。不得重新做字段提取。
- 草稿块为空但 MinIO 有原件或已确认索引请求：先确认是否能按原方案库策略重建块，并列明会恢复的内容；如需重新解析，应单独执行并复核结果，不能静默改用新分块规则。
- 图片缺失：列出具体 `document_id`、图片对象键和引用它的块；从对应原文件/备份只补传缺失图片，不批量重传全部文档。
- PG 草稿、文档状态、版本或 `source_id` 冲突：先人工核对源记录，不能通过重建自动改写 PG 关联。
- MySQL 记录没有有效草稿覆盖：按 MySQL 来源写为 `mysql`；若其自身无效或关联冲突，单独列出并要求处理。

补齐来源后重新执行只读预检。仅当报告中的每项缺失已解决，或管理员明确接受该份**精确缺失清单及其影响**，才进入恢复。新缺失不能由旧确认自动放行。

### 3. 恢复到影子 Collection

提交本次 `preflight_id` 和对应缺失指纹，启动 `solution` 恢复。恢复期间通过 PostgreSQL 跨进程写栅栏阻止该知识库的发布、下架、删除、索引和 MySQL 同步写入；查询仍走旧 Alias。

恢复顺序：

1. 先用已发布管理员草稿中的最终字段、原 `mysql_id`/`source_id` 和 `source_blocks`，通过既有索引构建链路写 `admin_draft` 及其附件块。
2. 对未被有效管理员草稿覆盖的有效 MySQL 记录，写入 `mysql`；按 `mysql_id` 去重，绝不为有有效 `admin_draft` 的记录再写 `mysql`。
3. 对已接受的不可恢复来源仅按报告跳过并保留审计；出现新缺失、非预期版本、分块/embedding 失败或任一批次失败时，任务失败且不得切换 Alias。
4. 写入后 flush/load 影子库，校验 schema、Loaded 状态、行数和完整预期主键集合；恢复报告必须说明业务记录、附件块和跳过项数量。

### 4. 管理员确认切换

影子库验证完成只表示 `READY_TO_SWITCH`，不表示已经切换。管理员先核对：

- `admin_draft` 与 `mysql` 的 `mysql_id` 无重复；所有有效 PUBLISHED 草稿均在恢复清单中；原 `source_id` 保持一致；
- 需要恢复的附件/图片引用均已校验，原件下载能力与向量正文恢复能力分开报告；
- 影子库行数/主键校验通过，跳过项与管理员接受的清单完全一致；
- 恢复期间来源快照未变化，活动 Alias 仍指向预检记录的旧 generation。

只有管理员显式确认后，系统才执行切换：先把旧活动物理库改名为带任务标识的备份；如果 `solution` 原名被另一旧 Collection 占用，也先将其改名保留；再把新影子库改名为 `solution`，最后让 `kc_public_solution` Alias 指向 `solution`。确认时重验来源或影子库失败时，不改名并保持旧 Alias。改名/切换中途出错不会删除任何 Collection，任务记录备份名供核对；切换后旧物理库继续保留，不得在新库已接收写入后盲目切回旧库。

### 5. 切换后验收

- 管理控制台确认任务为 `SUCCESS`，`solution` 物理 Collection 已是新数据，`kc_public_solution` Alias 指向 `solution`，旧活动库以备份名保留；其他四个 Collection 和业务数据库未被改动。
- 抽查管理员确认过的方案：核对方案字段、`mysql_id`、原 `source_id`、来源附件和图片；验证原文件下载（若对象原本缺失且未补传，应明确显示该文件不可下载）。
- 对代表性方案执行检索，核对卡片、详情、图片和完整正文；验证不会同一 `mysql_id` 同时展示 `admin_draft` 与 `mysql` 两份业务结果。
- 记录新旧 generation、任务 ID、行数、跳过清单、验收样本和旧库保留位置。观察稳定后再另行决定是否清理旧库；清理不是重建流程的一部分。

## 五、停止条件与回退

任一条件成立时立即停止，不切换 Alias：预检无法完整枚举来源；PG/MinIO/Milvus/MySQL 依赖不健康；影子库容量不足；来源或缺失指纹变化；有效 PUBLISHED 草稿、版本、关联或预期主键无法解释；同一业务记录出现 `admin_draft`/`mysql` 重复；schema、行数、主键或 Loaded 校验失败。

停止后旧 Alias 和旧 Collection 必须继续服务，保存失败任务、错误和影子库供诊断。只有在新库尚未承接写入且核对来源一致时，才可由管理员评估切回旧 generation；切回不是自动动作。不要为“让页面恢复”而删除缺失记录、将草稿改成未发布或重跑 LLM。

## 六、当前已知限制

- 代码包含影子恢复与来源核验逻辑；本轮最后补充的版本替换、失效图片过滤、发布版本并发校验及显式字段清空尚未重跑后端测试。本轮只做了 Python AST 语法检查和 `git diff --check`，不能据此称完整回归通过。
- 该方案尚未对真实服务器 PostgreSQL、MySQL、MinIO、Milvus 做端到端验证，服务器部署版本也需现场核实。
- 现有自动校验包含 schema、行数、主键及来源快照；生产切换前仍需要人工抽样检查语义检索、附件下载和图片展示。
- 旧审计导出包 `vector-audit-current-20261016-145155` 只是当时快照。必须在最新数据上重新预检；此前“22 份有 source_blocks”等统计不能替代当前报告，也不能假设这 22 份都已完成附件对象核验。
- 真实跨进程写栅栏、Milvus Alias 原子切换、资源峰值和全链路回退都需在生产变更窗口验证；没有完成前不得宣称重建已安全上线。
