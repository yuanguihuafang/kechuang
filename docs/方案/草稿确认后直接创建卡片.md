# 需求、方案与成果建稿及多事项确认

## 目标

用户进入需求、技术方案或科研成果建稿流程后，依据独立事项数量处理：单项直接生成草稿；多项先简短列出各项摘要，并确认拆分或合并后再创建。确认前不创建或展示草稿卡片。

## 行为约定

- 多事项摘要每项单独一行，格式为“实际名称：核心内容”；不编号，不显示“名称：”或“描述：”字段标签，也不把名称和内容拆行。

- 范围包括需求、技术方案和科研成果草稿，不限于用户选择快速入口后的文件上传；普通对话由 Agent 按每轮表达判断是否进入建稿流程。客户拜访记录不适用多事项拆分。
- 普通对话中用户明确要求“整理草稿/生成草稿”时，必须进入对应建稿判断并实际调用草稿工具；只有结构化工具成功结果才能驱动卡片展示，不能只回复文字总结或声称已有草稿。外部用户只能处理需求、方案或成果；客户拜访草稿数据不得注入外部会话上下文或出现在公开响应中。
- 仅识别出一个独立事项时直接生成或更新一份草稿；没有可用事实时才追问补充。供需匹配、知识检索和普通资料解析不自动创建草稿。
- 建稿流程先检查本轮文字和完整关联材料。多个彼此独立且足以单独成稿的事项，按原文顺序逐行简要列出“名称—核心内容”，询问“拆分生成 N 个草稿，还是合并为 1 个草稿”，响应状态为 `DRAFT_MULTI_CONFIRM_REQUIRED`。同一事项的章节、功能和步骤不拆分；确认前不得创建、修改、保存、发布或展示草稿卡片。无明确选择时继续询问。
- 用户选择拆分后分别创建 N 份并展示全部卡片；选择合并后完整涵盖全部事项生成一份。用户已明确选择时不重复追问，也不追问补充/修改什么。仅在真实草稿工具成功返回结构化草稿后展示 `draft_card`。
- 上传解析进入意图确认或多事项确认时，完整解析原文与文件名按会话暂存，30 分钟过期；下一确认轮作为不可信业务资料提供给 Agent，确认流程结束后清除。摘要仍可供用户阅读，但不能替代多事项判断或确认轮的完整原文。
- 仅在真实草稿工具成功返回结构化草稿后展示 `draft_card`；工具失败时如实提示，不生成伪卡片、不声称成功。

## 草稿与附件的 Milvus 关联标识

- 新发布草稿的 `source_id` 由来源批次稳定生成并写回草稿 JSON，不依赖草稿 `mysql_id`；同一上传文档解析出的多条草稿及其文档原文块共用一个 `source_id`，不同上传批次互相独立。
- 草稿块仅写 `mysql_id + source_id + chunk_role`，`document_id` 为空；文档块仅写 `document_id + source_id + chunk_role`，`mysql_id` 为空；MySQL 同步块仍仅以 `mysql_id + chunk_role=mysql` 定位且 `source_id` 为空。
- 更新草稿只替换同一 `mysql_id` 的草稿角色块，不删除关联文档块；按 `source_id` 删除仍清除该组草稿及文档块。删除流程优先使用草稿中持久化的 `source_id`。
- 旧索引不迁移、不重建。恢复没有持久化 `source_id` 的旧发布草稿时，带附件数据继续按旧附件 ID 哈希生成关联值；无附件旧草稿使用稳定 `mysql_id`。现有 collection 字段足以承载新约定。

## 同一会话的多草稿与附件索引

- 草稿分别保存在 PostgreSQL 草稿记录中，以 `draft_id` 区分；同一 `thread_id` 可关联多条草稿。会话回复将该会话当前用户可见的草稿按更新时间倒序返回，前端现有分页默认显示最新草稿。
- 每个会话只保留一个当前活动草稿 ID；新建草稿必须生成独立 `draft_id`，不得按用户、会话和类型隐式覆盖其他草稿。保存/编辑必须指定目标 `draft_id` 和版本。普通对话新建走独立创建语义；文件解析识别出多个独立事项时，每个事项都创建独立草稿，不复用或覆盖同会话同类型草稿。批次写入必须全成或全败，失败时不得留下部分草稿；响应中的 `draft_ids`、`draft_previews` 保持原文事项顺序，首项为本轮默认活动草稿，并保证会话按更新时间倒序加载时首项仍显示在首页。
- 会话状态另存轻量 `draft_index`（序号、草稿 ID、标题、类型、状态、版本），序号在草稿创建/批次响应顺序中固定；普通会话轮次只向 Agent 注入索引，不注入其他草稿正文。卡片继续按更新时间倒序分页，但标题同时显示固定的“草稿 N”编号；用户明确说“草稿 N”时按此编号定位，页面“第 N 页”不得当作草稿编号。“第 N 份”只有在对话中展示顺序明确且仍可确认时才按该顺序定位；按标题定位仅在唯一或指向明确时使用对应 `draft_id`；无法唯一对应时先追问标题或内容，不猜测。未明确指定目标且说“当前草稿”时才使用 `active_draft_id`。既有卡片编辑继续直接按卡片携带的草稿 ID 操作，不新增数据库表。
- 若会话已有未发布草稿，仍遵循现有“确认更新还是新建”规则；用户确认新建后，一次确认创建整批事项，旧草稿保留，不按批次内每个事项重复追问。后续对某一页草稿的编辑/发布必须使用该页对应的 `draft_id`。
- 多项草稿只共享明确适用于整份资料的公共字段和附件；单项专属字段只写入对应草稿。字段归属不明确时保留原文/留空并提示核对，不推测或把一项字段覆盖到其他项。
- 同一提取批次的草稿有独立 `draft_id` 和发布后的 `mysql_id`，但与原文档共用批次 `source_id`；草稿向量按各自 `mysql_id + source_id + chunk_role` 区分，文档原文块按 `document_id + source_id + chunk_role` 关联。发布或更新一条草稿不得覆盖同批次其他草稿；更新只替换目标草稿块并保留共享原文块。
- 管理台删除批次中的任一草稿时按共享 `source_id` 硬删除整组草稿、已发布业务记录和相关向量，不要求先下架；共享附件/文档存储仅在确认没有批次外引用后删除。普通用户的发布/下架权限不因此改变。旧数据没有批次标识时沿用原有单草稿/文档关联规则，不迁移或重建旧索引。
- 当前有未发布草稿时，若用户明确要另建或本轮内容明显是独立的新事项，Agent 先提醒该草稿尚未发布、其他用户暂时不可见，并询问是否确认新建；确认前不创建或修改草稿。确认新建后，旧草稿保留并挂起，新草稿成为唯一活动草稿；后续默认只更新活动草稿。若用户明确要求继续完善活动草稿，则只按其 `draft_id` 保存；目标不清楚时先询问，不猜测切换。
- 用户明确要求发布且当前活动草稿唯一时，Agent 可直接调用 `kc_draft_publish(draft_id)`，不再追加确认；多份草稿或目标不明确时先询问目标。讨论发布、表达将来计划或询问如何发布不触发工具；只有发布工具成功后才告知已发布。发布后的草稿仍按下方更新/新建确认规则处理。
- 用户在已有已发布草稿的会话中继续提交草稿相关文字或文件时，Agent 先判断是更新最近发布的草稿还是新建，并说明判断、询问确认；确认前不调用创建、保存或检索工具。明确要求发布当前草稿时不走更新/新建追问，按准确 `draft_id` 调用发布工具。用户选择更新时用 `kc_draft_save(draft_id, expected_version)`；选择新建时用 `kc_draft_create`，生成独立草稿。
- 保存已发布草稿的更新会保留未改字段、原附件、解析原文块及关联标识，并转成可再次发布的草稿状态；上传材料不会被接口静默追加到已发布内容。
- 同一上传批次的草稿块和附件原文块共用稳定 `source_id`；批次内草稿依靠各自 `mysql_id` 区分，批次之间的 `source_id` 独立。
- 草稿块仅写 `mysql_id + source_id + chunk_role`，`document_id` 为空；文档块仅写 `document_id + source_id + chunk_role`，`mysql_id` 为空；MySQL 同步块仍仅以 `mysql_id + chunk_role=mysql` 定位且 `source_id` 为空。
- 更新草稿只替换同一 `mysql_id + chunk_role` 的草稿块，不删除关联文档块；按 `source_id` 删除会清理该批次的所有草稿和文档向量。管理台删除草稿还要清理未被批次外记录引用的文档目录与附件存储对象；共享附件必须保留。
- 旧索引不迁移、不重建。旧草稿通常有附件；恢复未持久化 `source_id` 的旧草稿时，先从已有草稿向量按 `mysql_id + chunk_role` 读取真实关联值，未查到再按旧附件 ID 哈希兼容。现有 collection 字段足以承载新约定。

## 验收

需求、方案、成果进入建稿流程（无论快速入口、普通对话或文件上传）时均检查多事项；单项直接生成，多项先列项并确认拆分/合并，确认前不得创建/修改/保存/发布或展示草稿卡片。普通问答明确要求整理草稿时必须得到真实工具结果后展示卡片；外部用户不接触客户拜访记录相关功能或内容。确认后按选项生成并返回所有草稿卡片；客户拜访不拆分。无业务入口且只上传文件时仅返回资料摘要，不猜测意图、不建稿或检索；完整原文按会话暂存 30 分钟，后续明确进入草稿流程时按当前意图从完整原文提取，不能依赖摘要。明确入口、待续快速入口和活动草稿流程不变。已发布草稿之后的更新/新建仍须遵循既有目标确认规则。会话草稿索引保证序号稳定并按序号/唯一标题定位；目标有歧义时先追问，默认活动草稿只用于未指定具体目标的续改。会话按更新时间倒序分页显示，默认活动草稿稳定。删除任一批次草稿按共享 `source_id` 清理整组关联数据；旧草稿及 MySQL 同步数据保持兼容。实际模型/MCP 运行仍需页面回归确认。

## 本地实现与验证

- 文档字段提取沿用 Perception 的多事项结果；同批草稿通过单事务批量写入 PostgreSQL，每项独立 `draft_id`，以任务级 `source_id` 关联。创建响应按原文顺序返回，现有会话草稿分页按更新时间倒序展示。
- 管理台删除批次成员时先按精确 `source_id` 收齐并预检全组，再清理业务记录和向量；无论成员是否已发布都直接整批硬删除，附件/文档仅在不存在批次外引用时删除。无 `source_id` 的旧记录继续按旧单条路径处理，不重建 Milvus。
- Backend 保留显式草稿入口的现有指令，并在会话状态中短暂保存待确认的完整材料；Agent SOUL 与需求/方案/成果三个 Skill 源文件及本地备份副本共用多事项规则。匹配、检索和客户拜访流程不进行多事项拆分。
- 当前实现已覆盖 Backend 建稿流程和前端多草稿卡片呈现；早期仅修改 Agent/Skill 的范围记录不代表当前完整实现范围。
- Backend 全量测试 857 项通过，另有 1 条 Starlette 弃用警告；未调用真实模型/MCP，也未验证服务器或小程序端到端流程。
