# 需求类型草稿写入与编辑文案

## 目标

- 用户在快捷入口显式选择需求类型后，该值进入会话上下文，并在创建需求草稿时写入持久化字段 `fields.category`。
- 用户未选择类型时，不根据默认值或模型猜测补写类型。
- 需求草稿编辑器统一显示“编辑需求”，不再假设所有需求都是采购。

## 当前根因

需求类型选择通过 `draft_context.demand_type` 进入会话。MCP `kc_draft_create` 当前只从工具参数中的 `draft.fields` 保存业务字段；如果模型遗漏 `category`，显式选择值没有进入草稿。

## 实现边界

- 草稿创建服务端从当前会话已保存的显式 `demand_type` 读取值；仅当草稿类型为 `demand` 且 `category` 尚未由草稿字段明确提供时写入 `fields.category`。
- 不改变供给草稿、未选择类型的需求草稿或用户已明确填写的类别。
- 只调整科创测试界面的“编辑需求”标题；不修改前后端请求字段、API 路由或 OPIEos/DeerFlow 核心。

## 验收

- 已选择类型但模型草稿遗漏 `category`：工具返回和持久化草稿均包含所选值。
- 未选择类型：不注入默认 `category`。
- 模型/用户草稿已明确填写类别：保留已有值。
- 草稿编辑器标题显示“编辑需求”。
- 后端草稿工具测试、前端回归测试和构建通过。

## 实现与验证

- `backend/runtime/mcp_tools/draft.py` 的 `kc_draft_create` 从同一用户会话的 `chat_flow.request_context.draft_context.demand_type` 读取已选类型；仅对需求草稿、且草稿未给出类别时写入 `fields.category`。不会跨用户读取，也不会为未选择类型添加默认值。
- `frontend/src/pages/supervisor/BusinessBlocks.jsx` 仅将需求编辑器标题改为“编辑需求”；其他草稿类型沿用各自标题。
- `backend/tests/test_mcp_draft_tools.py` 覆盖选中类型写入、已有类别保留、未选择不推断及会话所有权隔离。
- 验证：后端完整测试 `530 passed`（1 条现有 Starlette/httpx 弃用警告），定向 Ruff 与 Vite 构建通过。
