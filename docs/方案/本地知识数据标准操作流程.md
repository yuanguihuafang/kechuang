# 本地知识数据标准操作流程

适用于本地管理控制台的文档、草稿、发布、问答和索引维护。本文约束应用流程；不代替生产变更审批，也不代表服务器已同步。

## 数据归属

| 数据 | 权威存储 | 规则 |
| --- | --- | --- |
| 文档、版本、解析状态、草稿、确认分块 | PostgreSQL | 以活动版本和草稿状态为准；重解析期间旧结果不可作为当前结果展示。 |
| 已发布业务记录 | MySQL | 仅已发布草稿写入；沿用稳定业务 ID，重试不创建重复业务行。 |
| 原件、解析产物、图片及图片清单 | MinIO | 引用对象必须真实可读；图片统一由 `document_id + image_id` 生成 `/api/v1/perception/images/{document_id}/{image_id}`。 |
| 检索索引 | Milvus | 派生数据，可从有效的 MySQL、PostgreSQL 和 MinIO 来源重建；不得把未发布内容作为公开知识。 |

## 日常操作

1. **上传**：确认知识范围和类型，上传后检查文档目录中的文件名、文档 ID、解析状态及附件版本。同名文件再次上传形成新版本；在新版本发布前，仍被已发布草稿引用的旧版本继续有效。
2. **重新解析**：解析任务开始后，界面清空旧解析原文、旧分块和旧字段提取结果；PostgreSQL 中已保存草稿字段不因解析而覆盖。分块和字段提取是独立步骤；只有显式提取才更新提取结果，发布前确认字段、来源附件版本和封面图。
3. **发布**：发布前预检必须确认附件归属及活动版本、MinIO 原件和解析产物、正文/封面图片引用对象、稳定 MySQL 身份、嵌入与 Milvus Collection 可用。预检失败时不得写 MySQL 或索引；查看错误并修复来源后重试。发布成功后核对 PostgreSQL 状态、MySQL 记录数/ID 与 Milvus 来源组。失败不能混合展示旧解析结果与待发布新结果。
4. **修改/下架/删除**：先按文档 ID 和草稿 ID 确认目标及共享附件引用。下架要求填写原因并同步状态/审计记录；共享附件仍被已发布草稿引用时保持可检索。用户删除是逻辑删除，个人中心立即隐藏，资源暂存；管理员手动彻底删除功能仍保留。不得手工只删单个存储中的数据。
5. **问答验收**：分别用已发布与未发布资料验证；只应检索当前身份有权访问的已发布内容。无相关知识库候选时按策略尝试联网搜索，不能把无关候选当成命中。图片需可读取且属于命中证据所在文档/页；不可读图片应被省略，不影响文本证据。卡片最多展示 3 张图片，详情显示完整命中内容。

## 定时清理边界

- 用户逻辑删除草稿在删除请求后立即对个人中心隐藏；该请求不立即物理删除数据。**产品决定暂不启用用户草稿 30 天静默清理，但当前本地 `temporary_materials.py` 仍在每日北京时间 02:00 清理满 30 天的已删除草稿，并清理连续 30 天未更新的 `CONFIRMED/PENDING_REVIEW` 草稿附件（保留草稿字段）。这是产品决定与代码现状的差异，修改/部署前必须先关闭或重新确认该策略。**
- 企业库/专家库未发布来源仍有独立的 30 天过期规则；不能据此推断其他类型管理员文档也会自动清理。
- 孤儿对象在统一清理时段按配置的宽限期检查，并在删除前重新核实 PostgreSQL 引用；已发布数据所引用的原件、版本、图片和解析产物必须保护。
- 审计记录默认保留 180 天；管理员手动彻底删除与后台定时清理是两条不同操作路径。

## 索引恢复 / 整库替换

服务器升级后由管理员在数据管理页按顺序操作：

1. 点击**检查可恢复来源**（只读预检），记录可恢复来源、MySQL 记录数及不可恢复项。刷新前后端版本后重新检查；不可恢复项须先按文档 ID、草稿 ID 和 MinIO 对象键逐条处理。
2. 确认检查结果稳定后，点击**确认并恢复影子 Collection**。恢复应写入影子库，不改当前活动 Collection；等待任务完成并检查失败明细。
3. 对比影子库与当前库：按知识类型核对记录数、业务 ID/source_id、发布状态、来源文档、分块数和图片引用。抽查关键问答及图片可读性。数量一致本身不等于内容正确。
4. 只有对比通过后才执行**替换/重建**。确认 Alias/活动 Collection 指向新库，并再次核对计数及问答；失败时保留旧活动库，按任务记录重试或回退。

## 故障处理与边界

- 图片或解析产物缺失：先按文档 ID 检查原件、活动版本、MinIO manifest 和对象键；原 PDF 可用时可只重解析/重分块，保留已确认的草稿字段和业务身份，再通过发布流程整体替换相关来源组。
- 原件缺失：从本地原始目录或可信备份找回后补回正确对象键并校验；不要把外观相近但无法确认的文件映射到原文档。
- PostgreSQL、MySQL、MinIO、Milvus 不存在分布式原子事务。预检只能降低部分写风险；写入中断仍须依赖任务状态、固定 ID 和显式重试，不能把单个接口 200 当作全链路一致。
- 日常读取不得隐式修补或写回清单。恢复和重建是显式管理操作，执行前先保留可恢复备份，并在任务完成后核对结果。
- 本地代码通过测试不等于生产验证；部署后须确认所有后端进程运行相同版本，并在目标环境重新预检。
