# 新项目独立部署与数据迁移执行方案

> 状态：执行方案草案  
> 适用范围：基于现有科创系统建立一套独立项目；前端、后端和各数据空间逻辑隔离；初始数据从现有项目复制，之后新项目上传自己的文件并独立更新。PostgreSQL、Milvus、MinIO 可共用服务实例，但必须使用独立数据库/ Bucket。  
> 边界：本文只规定本地规划和实施顺序，不代表已创建资源、迁移数据或部署服务器。

## 1. 目标和约束

1. 新项目有自己的前端和后端服务，发布、会话、用户业务操作不写入旧项目。
2. PostgreSQL、MySQL 和 Milvus 的表/字段/向量 Schema 与当前项目一致，但连接目标和后续数据独立。
3. 新项目初始知识库可以从当前项目复制一份；新上传文件按新项目的正常上传、解析、确认、发布和建索引流程处理，生成自己的文档、版本和图片 ID。
4. PostgreSQL、Milvus、MinIO 可共用服务实例以节省资源；新旧项目必须使用不同 PostgreSQL database、Milvus database 和 MinIO Bucket。初始复制的 PostgreSQL/解析清单所引用对象必须复制到新 Bucket 并校验。
5. 不修改 OPIEos 源码，不覆盖旧项目的配置、数据库、Collection、对象或运行数据。
6. PostgreSQL 全量克隆会同时带入用户关联记录。新项目用户不同，因此只能在隔离的暂存数据库中先做全量恢复，再根据确认的迁移清单保留公共知识数据、清理或映射用户专属草稿/会话/身份关联后，才允许新项目对外开放。

## 2. 推荐架构与数据边界

| 组件 | 新项目目标 | 初始迁移规则 |
| --- | --- | --- |
| 前端 | 独立构建和域名 | 使用新后端 API 根地址，不复用旧项目运行配置 |
| Backend | 独立进程/容器 | 独立配置、日志、任务和健康检查；禁止指向旧项目写库 |
| PostgreSQL | 同一服务实例中的独立 database | 先在 staging 全量恢复；按数据清单保留公共知识文档/版本/来源元数据，隔离或重建用户级会话、草稿和权限数据 |
| MySQL 用户身份库 | 新数据库或新表集 | 保持字段结构，写入新项目自己的用户；用户 ID 与旧项目的映射规则必须明确 |
| MySQL 业务库 | 新数据库或同库新表集 | 表名/字段沿用当前合同，连接配置指向新数据；同步和 CRUD 全部只操作新目标 |
| Milvus | 同一服务实例中的独立 database | 复制目标 Collection 的 Schema、索引和初始记录；之后只由新项目后端维护 |
| MinIO | 同一服务实例中的独立 Bucket | 初始知识库对象按 PostgreSQL 引用清单复制；新上传对象写入新项目 Bucket |
| OPIEos / DeerFlow | 按当前部署方式调用 | 不改 OPIEos 源码；新项目若共用 Gateway，必须单独确认 Agent、用户身份和运行时会话隔离 |

当前代码中业务 MySQL 表名由 `backend/core/contracts/mysql_schema.py` 固定定义，连接库由 `MYSQL_DATABASE` 等配置决定。因此可以在新数据库里创建相同表名和字段；若要给每类知识改成不同表名，则需要同步修改该契约及其所有读写/同步调用，不能只改环境变量。

当前公开 Milvus Collection 名称包括 `enterprise`、`expert`、`demand`、`achievement`、`solution`，另有 `inner`；公开别名为 `kc_public_<knowledge_type>`。新旧项目可在同一 Milvus 服务实例中使用不同 Milvus database，并沿用相同 Collection 和别名名称；对新项目重建或切换 Alias 不会影响旧项目。当前后端已有 `MILVUS_DATABASE` 配置项。

## 3. 端口和访问方式

1. 同一台主机上，两个进程不能绑定相同的“主机 IP + 端口”。建议由 Nginx 按域名分流，对外共用 HTTPS 443，内网 Backend 使用不同端口。
2. 若新旧 Backend 都直接发布宿主机端口，先检查实际占用，再分配不同端口。当前代码默认 Backend `8793`、管理前端 `8794`；新项目端口需按部署现场选择，不把示例端口视为已确认值。
3. 共用 PostgreSQL 实例时，新项目建独立 database，两个后端连接各自 database；无需第二个 PostgreSQL 容器，也无需增加 PostgreSQL 主机端口。若部署物理独立实例，才需要检查宿主机映射端口冲突。
4. 共用 Milvus 实例时，新项目使用独立 Milvus database；内部服务地址和端口可共用。只有部署第二个 Milvus 实例时，才需要另分配宿主机映射端口。
5. 共用 MinIO 实例时，新项目创建独立 Bucket，并使用单独凭据/策略；服务 API/Console 端口可共用。只有部署第二个实例时，才需要另分配主机端口。
6. MySQL、Attu 和管理端口也按同一规则检查，不要只检查 Web 页面端口。
7. 反向代理只公开前端/API 所需入口；PostgreSQL、MySQL、Milvus、MinIO 等数据端口仅允许应用网络访问。

## 4. 执行步骤

### 阶段 A：盘点与冻结方案

1. 确认新项目部署主机、域名、是否与旧项目同机、是否 Docker 部署，以及可用磁盘和备份位置。
2. 导出现有运行配置的非密钥清单：Backend 端口、`DATABASE_URL`、`MYSQL_DATABASE`、`MYSQL_IDENTITY_DATABASE`、`MILVUS_URI`、`MILVUS_DATABASE`、MinIO Endpoint/Bucket、前端 API 地址；密钥只在目标环境安全配置，不写入文档或命令输出。
3. 盘点 PostgreSQL 表和数据归属，至少标记：公共文档/版本/解析元数据、管理员/用户草稿、会话、任务、审计、临时数据、权限和身份映射。确认新项目要继承哪些公共资料、是否继承管理员草稿。
4. 盘点 MySQL 身份表和各业务表，确认新项目用户 ID 是否可能与旧项目重号，以及新库中 CRUD 和索引同步使用的表名与字段。
5. 盘点 Milvus 每个 Collection 的 Schema、向量维度、索引、Alias、实体数和 Collection 内 user/scope 字段。确认 `inner` 集合是否包含必须继承的内容及其访问范围。
6. 盘点 PostgreSQL/MinIO 的文档对象键和图片/解析产物引用。确定初始知识库需要的原件、解析产物和图片清单。
7. 明确后续同步方向。推荐新旧项目各自独立写入；如需持续把旧项目数据推送给新项目，限定为单向同步，并定义数据类型、增量游标、删除/下架事件、冲突处理和重试规则。禁止默认双向覆盖。
8. 形成迁移对象清单、端口清单、配置差异表、回滚负责人和验收人；未明确的数据归属不得进入迁移写入阶段。

### 阶段 B：备份旧项目

1. 选择一致性窗口：短暂停止相关写入，或为 PostgreSQL、MySQL、Milvus、MinIO 使用可对齐的快照/备份方案并记录统一时间点。
2. 备份 PostgreSQL、MySQL、Milvus/etcd/MinIO 所需数据、项目配置和数据库迁移版本。只备份本次迁移需要的资源；不把密码或 Token 写入报告。
3. 对备份文件生成 SHA-256 清单，并执行格式可读性检查和恢复演练（至少在临时目标恢复 PostgreSQL）。
4. 记录旧系统各知识类型的 MySQL 行数、PostgreSQL 文档/版本数、Milvus 各 Collection 记录数、MinIO 对象数/容量、当前 Alias 指向和快照时间。
5. 备份未验证、空间不足或数据一致性时间点不清楚时停止，不进入正式复制。

### 阶段 C：建立新项目基础资源

1. 创建独立部署目录、Backend 服务、前端服务、日志目录和数据卷；配置独立域名/反向代理路由。
2. 创建独立 PostgreSQL 数据库并用项目现有 Alembic migration 建立表结构。准备恢复整库的 staging 数据库，正式目标库不可直接作为第一次试验目标。
3. 创建独立 MySQL 用户身份库和业务库/表，导入当前版本对应的 Schema；给新项目账号最小必要权限，禁止连接旧库写入。
4. 在现有 Milvus 服务实例中创建新项目专属 database，使用当前代码定义的字段、向量维度和 Collection Schema；实例地址可共用，database 名必须独立。
5. 在 MinIO 服务实例中创建新项目专属 Bucket，配置独立凭据和访问策略。
6. 分配互不冲突的端口；配置文件使用新资源地址。当前后端配置变量名按代码核实，至少包括 `DATABASE_URL`、`MYSQL_*`、`MILVUS_URI`、`MILVUS_DATABASE`、`MINIO_*`、`APP_PORT`、`PUBLIC_API_BASE_URL` 和 CORS 来源。
7. 在启动服务前核对配置解析结果，确保所有写连接只指向新项目。不给旧项目做任何配置改动。

### 阶段 D：复制并整理初始数据

1. 将完整 PostgreSQL 备份恢复到隔离的 staging 数据库，不直接对外服务。
2. 从 staging 数据库按阶段 A 清单导出/保留公共知识库文档目录、活动版本、解析产物引用、发布来源和必要权限元数据；删除或重新建立不该继承的用户会话、草稿、临时任务、身份关联及旧项目专属状态。每类删除/保留都先做数量预览并由负责人核对。
3. 复制 MySQL 用户身份和业务数据时，严格按新项目的用户迁移决定执行。若用户集合全新，则创建新用户数据，不复制旧用户的私有业务记录；如确需历史业务记录，先生成旧 ID 到新 ID 的映射并验证无重号、无悬空外键。
4. 将旧项目目标 Milvus Collection 的 Schema、索引、Alias 及批准迁移的初始记录复制到新项目 Milvus database。保留新旧记录之间可追踪的 source/document IDs；若用户级向量也要复制，先确认 owner/scope 规则并在新系统验证权限过滤。
5. 按保留的 PostgreSQL 引用清单，把旧 MinIO 的原件、图片、图片清单和 MinerU 解析产物复制到新项目 Bucket；保持对象键不变或更新所有引用，不允许只复制 metadata、不复制对象本体。
6. 为多存储复制建立迁移清单：源/目标 ID、对象键、字节数、哈希、记录数、失败原因。禁止因同名文件自动替换；所有 ID 映射必须明确、可回查。
7. 如果迁移期间旧项目仍在写入，按统一快照时间点补做增量同步；同一对象/记录按版本和更新时间幂等处理，不以“最后写入者胜出”静默覆盖冲突。

### 阶段 E：切换前校验

1. PostgreSQL：检查 migration 版本、关键表计数、外键/引用、活动文档版本、用户/草稿归属和状态。
2. MySQL：检查表结构与 `mysql_schema.py` 契约一致；用测试用户验证创建、查询、更新、删除和同步只访问新库。
3. Milvus：逐 Collection 对比 Schema、索引、Alias、计数和关键 source_id；确认没有目标项目无权访问的数据。
4. MinIO：根据 PostgreSQL 引用清单核对迁移对象数量，并抽样校验大小和哈希；通过新项目图片标准路径读取封面图和解析原文图片；下载原件及解析产物。
5. 检索：使用旧项目已知问题和新项目新文件分别验证命中、知识类型、发布/下架过滤、来源文档、图片路径和权限边界。
6. 上传新文件：在新项目前端上传一份测试文档，完成解析、确认、发布，验证新 ID、新对象键、新 PG 记录、新 MySQL 业务数据（如适用）和新 Milvus 分块均落在新项目；确认旧项目计数和内容未变化。
7. 运行健康检查、后端日志检查和前端主要流程检查。全链路验收通过后再对外开放。

### 阶段 F：上线、同步与回滚

1. 上线前再次记录新旧端点、数据库名、Collection/Alias、Bucket/前缀和版本号；应用、代理、数据源分别核对。
2. 如需持续同步，先以 dry-run/只读模式核对待同步数，再按单向、幂等、可重试的规则启用；每批记录处理数、跳过数、失败数和水位。删除/下架需使用显式事件或墓碑状态，不能只同步新增和更新。
3. 上线初期观察解析、发布、同步、检索、图片读取和清理任务；确认没有跨项目写入后再恢复正常流量。
4. 回滚触发条件：新项目出现跨用户/跨项目数据、旧项目被意外改写、索引/图片来源大面积不一致、数据库迁移失败或核心问答无法使用。
5. 回滚时将新域名路由回旧前端/API 或关闭新项目写流量；不覆盖旧项目数据库和对象。新项目上线后产生的数据先单独保留，确认恢复方案后再处理，禁止直接把旧快照恢复到仍在写入的目标库。

## 5. 端口配置示例

下面只表示端口分配方式，不是已经核实的现场值：

| 服务 | 旧项目示例 | 新项目示例 | 对外建议 |
| --- | ---: | ---: | --- |
| Backend | 8793 | 8795 | Nginx 分域名转发；外部统一 HTTPS 443 |
| 管理前端 | 8794 | 8796 | 可由反向代理提供，不一定直接暴露 |
| PostgreSQL 容器内部 | 5432 | 5432 | 新旧 Docker 网络隔离；宿主机发布时使用不同端口，如 5432/5433 |
| MySQL 容器内部 | 3306 | 3306 | 只在内部网络访问；宿主机发布端口须先检查占用 |
| Milvus 容器内部 | 19530 | 19530 | 新实例可复用容器端口；宿主机映射不能冲突 |
| MinIO 容器内部 | 9000 | 9000 | 同一服务实例可共用端口，按项目使用不同 Bucket；公网只开放必要的代理入口 |

推荐方案共用 PostgreSQL、Milvus、MinIO 的服务实例，但为新项目创建独立 PostgreSQL database、Milvus database 和 MinIO Bucket，所以不会产生同一数据空间内的记录混写。物理上新建容器/实例也可行，但会增加资源、端口、备份和运维成本；仅在故障域、性能或安全要求需要时采用。

## 6. 上线验收清单

- [ ] 新旧 Backend 配置彼此独立；PostgreSQL database、Milvus database、MinIO Bucket 和 MySQL 业务/身份数据空间彼此隔离。
- [ ] 新项目公共知识内容与批准迁移清单一致；不需要的旧用户草稿、会话和私有业务数据不可见。
- [ ] 新上传文档使用新项目存储路径、文档/版本/图片 ID，并完成发布和索引。
- [ ] MySQL 查询、写入、同步和删除均落到新项目目标表。
- [ ] Milvus 新项目 Collection/Alias 与旧项目完全独立；重建或切换新 Alias 不影响旧项目。
- [ ] PostgreSQL 文档元数据、MinIO 对象键和 Milvus 来源 ID 能相互追溯。
- [ ] 新项目用户无法读取其他用户数据；旧项目用户和数据在本次上线前后不受影响。
- [ ] 端口、域名、CORS、图片公开地址、健康检查、备份和回滚步骤已实测。
- [ ] 已验证同步方向、删除/下架行为、幂等重试和冲突处理；未启用未经验证的双向同步。

## 7. 当前待现场确认

1. 新项目部署在同一台服务器还是另一台服务器，使用 Docker 还是现有 systemd/其他部署方式。
2. 新项目是否要继承全部当前公开知识资料、管理员草稿和内部 `inner` 向量数据。
3. “全量 PostgreSQL 复制”是否包含用户会话、用户草稿、审计和任务；新项目用户不同，默认不建议直接对外开放这些克隆记录。
4. 新 MySQL 用户表是独立数据库、独立表还是既有业务平台提供的新表；新老 user_id 是否共享编号空间。
5. 之后的数据同步是各自独立，还是旧项目单向推送到新项目；同步的知识类型及删除/下架规则。
6. 现场端口占用、TLS 域名、Nginx 配置、备份容量和数据库版本；是否需要物理拆分服务实例。

这些现场信息确认后，才能补上具体主机命令、Compose 配置和数据迁移命令；本方案不包含猜测的服务器路径、口令或生产端口。
