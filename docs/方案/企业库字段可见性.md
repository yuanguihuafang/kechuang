# 企业库字段可见性

## 目标

除系统字段外，企业库业务字段全部同步到 Milvus。外部人员仅隐藏 `created_by`（创建人）和 `business_scope`（经营范围）；`social_staff_num`（参保人数）、`phone`（联系电话）、`email`（联系邮箱）和 `address`（通讯地址）对外可见。MySQL 业务表中的数据不删除、不改写。

## 权限与数据流

- 身份只使用服务端从已认证上下文解析出的 `user_role`，不接受请求参数指定角色。
- 只有 `created_by` 与 `business_scope` 属于企业库 `internal_fields`；其他业务字段属于 `public_fields`。
- 企业 MySQL 向量同步保留完整业务字段，内部用户可通过同一索引检索全部字段。
- 外部检索在进入重排和回答生成前，按企业库公开字段白名单裁剪结构化字段、字段清单与文本；无法确认字段清单的历史 MySQL 向量不返回。
- 旧文本向量按字段标签裁剪：字段标签允许行首缩进及标签与冒号间空白；无法识别的冒号字段行会关闭后续文本输出，直到识别到公开字段，避免沿用上一字段的公开状态泄漏内部内容。
- 外部用户请求企业库块详情时，直接回查的 MySQL 命中也必须在构造详情和调用摘要模型前按同一白名单裁剪；详情中的草稿正文不得包含创建人或经营范围。
- DeerFlow `kc_profile` 返回结构化企业画像时，生成推荐卡片/详情前也使用同一公开字段白名单；外部详情继续展示联系人、联系电话、联系邮箱等公开字段，只省略创建人和经营范围。内部画像不裁剪。

## 需求库模型上下文

- 外部用户的需求库检索命中在重排前剔除 `link_name`（联系人）和 `link_tel`（联系电话），不能只依靠最终回答脱敏。
- 结构化 MySQL 命中按需求库公开字段白名单重建文本；历史文本命中按字段标签裁剪，字段清单/边界无法确认时不向重排或模型传递该命中。
- 该过滤同时覆盖新索引和仍含内部字段的历史向量，不删除或改写 MySQL 数据，也不影响内部命中。
- 管理端的字段权限目录据同一 MySQL 字段合同生成，仅将创建人和经营范围展示为外部用户脱敏字段。

## 验收

- 除系统字段外，企业库 MySQL 同步产出的记录、文本和 `field_names` 包含全部业务字段。
- 外部响应的企业 MySQL 证据仅不含 `created_by`、`business_scope` 的键、字段名或字段值，仍保留其他公开字段。
- 外部企业库块详情及其摘要模型输入均不含 `created_by`、`business_scope` 的键、字段名或字段值。
- 外部需求检索在重排输入前已移除 `link_name`、`link_tel`，内部检索行为不变。
- 外部 `kc_profile` 企业详情保留 `admin_name`、`phone`、`email`，且不含 `created_by`、`business_scope`。
- 其他知识库和企业库的其他公开字段行为不变。
